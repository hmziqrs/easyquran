# Hard rules:
- Quran databases are all immutable. No modifications and never versioning.
- **`documentation/` is human-owned and untouchable.** It holds permanent records only (shipped contracts, finished-work records, research, methodology). Agents may read and cite it freely but never create, edit, move, or delete anything under `documentation/` — its files are created manually by the owner. A pre-commit hook refuses staged changes there unless the owner commits with `DOCS_OVERRIDE=1`. `docs/` is the hot tier: implementation plans that ship and then retire; when a hot plan is fully implemented and verified, the owner distils a permanent record into `documentation/` by hand.
- **`db/` is untracked and gitignored.** The Quran DBs live in R2 (`easyquran` bucket) and are provisioned onto disk out of band; they are never committed, never added back with `git add -f`. Anything that must survive a fresh clone cannot live under `db/`.
- **Toolchain = Vite+ (`vp`) running on bun.** Package manager is **bun** (workspace root): `bun install`, `bun.lock` is the only lockfile; pnpm-era files (`pnpm-lock.yaml`, `pnpm-workspace.yaml`, `.npmrc`) are gone and must not come back. `devEngines.packageManager` (bun range) in the root `package.json` is what Vite+ and its shims select — keep it at bun (`vp env current pm` proves the pick). The `vp` CLI bundles vite 8.3.1 / vitest 5.0.1 / oxlint / oxfmt; the project pins `vite-plus` plus the `vite` → `@voidzero-dev/vite-plus-core` catalog alias and the matching `vite` override — bump all three together. Catalog, `patchedDependencies`, and `trustedDependencies` live in the root `package.json`. Git hooks live in `.vite-hooks` via `core.hooksPath` (`prepare` runs `vp config`; inspect with `vp hooks status`).
- No SHA-256 over Quran data in any automated path (build, boot, runtime, ETag, cache, catalogue). A DB's identity is its **id**, never a hash. SHA-256 is manual audit only — three commands a human runs: `just quran-audit`, `bun run audit:arabic` (in `web/`), `bun run verify` (in `db/quran/translations` — a pipeline outside this repo's workspace). Crypto sha (CSRF, HMAC, Argon2, PKCE) is unrelated and stays. Don't re-add Quran sha — guards in `tests/quran_v1.rs` + `web catalogue-sha-guard.test.ts` fail the build (see documentation/quran-system.md — Hard rules).
- Always load and follow the `caveman` skill at the beginning of every session. Keep Caveman full mode active for every response. This rule is also applied to subagents.
- Reader navigation hrefs must preserve translation context: use the `surah*For(ctx,...)` family in `web/src/lib/data/quran.ts` (`surahPathFor`/`surahLocalPagePathFor`/`surahAyahPathFor`/`globalPagePathFor`/`juzPathFor`) with `ctx` from `surahRouteContext(sourceId)` or `routeContextFromParams(page.params)`. Never call the Arabic-only `surahPath`/`surahLocalPagePath`/`surahAyahPath` from a component, and never hand-build reader URL strings (no `/app` marker, no bare `/page|/juz|/t` literals). Machine-guarded by `web/src/routes/(application)/__tests__/nav-guard.test.ts` (`bun run test` in `web/`).
- Delivery divergences from `documentation/my-plan-raw.md`: translated reader routes (`/t/**` and `/{surah}/t/**`) are SSR + 7-day disk cache — never SSG; prerender stays Arabic-only, and production Quran bytes/size/path come from baked id maps, never remote metadata. Full record: `documentation/quran-system.md` Part 5 (Divergences from `my-plan-raw.md`).
- **No nested ternaries.** A `?:` may never appear inside another `?:` — not in either branch, not in a `$derived`, not in JSX/markup expressions, not in tests or `scripts/`. Use a named function with early-return `if`s (`function packLabel(): string { if (busy) return "…"; … }`), a lookup table (`XML_ENTITIES[c]`), or a first-match helper (`firstString(o, "last_seen", "lastSeenAt")`). A single flat ternary is fine. Machine-guarded by `bun run lint` (in `web/`).
- **Lint rules live in `web/vite.config.ts` → `lint.rules`** (`vp lint`/`vp check` read oxlint settings from that block; see https://viteplus.dev/config/lint). Rules there *extend* oxlint's defaults; type-aware settings live in the same block (`options.typeAware/typeCheck` + the `vite-plus` bundled `oxlint-tsgolint`). Never add a standalone `.oxlintrc.json` — `vp lint` does not use it, and passing it via `-c` *replaces* the default rule set, silently dropping other checks. Currently enforced beyond the defaults: `no-nested-ternary`, `unicorn/no-nested-ternary`, `no-shadow`, `prefer-promise-reject-errors`, `unicorn/no-array-callback-reference`, `unicorn/prefer-number-properties`, `no-floating-promises`, `no-misused-promises`.
- **All three gates are green and must stay green: `bun run check`, `bun run lint`, `bun run test` (run from `web/`).** `bun run lint` runs with `--deny-warnings`, so a warning is a failure.
- **`bun run check` is warning-free and must stay that way** — `svelte-check` runs with `--fail-on-warnings`, so an a11y or Svelte compiler warning fails the build. Never relax the flag to land a warning: fix the markup, or add a scoped `<!-- svelte-ignore rule_name -->` with a comment saying why the exception is correct. `tsconfig.json` also sets `noUncheckedIndexedAccess`, `noImplicitOverride`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUnusedLocals`, `noUnusedParameters` on top of `strict`.
- Prefer **es-toolkit** (`import { clamp } from "es-toolkit"` — named imports only, never `import * as`) over hand-rolling `clamp`/`groupBy`/`uniq`/`sumBy`-style utilities. It is `sideEffects: false` + ESM, so Vite tree-shakes per-function with no extra config. Check the real semantics before swapping — they are not always what the name implies: `inRange(v, min, max)` is **max-exclusive** and does no integer check, so it is NOT a drop-in for an inclusive `n >= 1 && n <= 114` bound, and 1-arg `clamp(v, max)` means *maximum*, not minimum. Keep the existing `trailingDebounce` (`$lib/storage`); do not swap it for es-toolkit `debounce`.
- All web keyboard shortcuts (cmdk, reader nav, any key-based action) use **TanStack Hotkeys** (`@tanstack/hotkeys`, pinned `0.8.0` — alpha) via the shared wrapper `web/src/lib/hotkeys.svelte.ts` (`registerHotkey()` over the `HotkeyManager` singleton). Never hand-roll `keydown`/`addEventListener`/`metaKey`/`isPaletteChord`-style handlers for app shortcuts. The library MUST be dynamically imported (`await import("$lib/hotkeys.svelte")`) from its consumer — never statically imported into an always-mounted component — so it stays out of the initial bundle. Gotcha: TanStack does not guard IME composition; any shortcut clashing with an IME session keeps its own `event.isComposing` early-return. Register from a client-only Svelte `$effect`, `unregister()` on cleanup.

# Dynamic context loading
Load relevant context ONLY when working on that area:

- **Rust backend** (`rust/backend/api/`): load `rust/backend/api/AGENTS.md` + `rust/backend/api/README.md` if exists.
- **Web** (`web/`): load `web/README.md` + Svelte skills (`svelte-core-bestpractices`, `svelte-code-writer`).
- **DB/migrations**: load `rust/backend/api/migration/README.md`.
- **Deploy**: load `deploy/README.md`.

Do NOT preload all context every session. Load on-demand based on files touched.

Always commit to the current branch unless I say otherwise.
