# EasyQuran — i18n (Paraglide) plan

Single source of truth for **UI** internationalization. This is the plan, not an index.

Scope of *this* doc: localize the **landing page** (`/`) and its shared chrome (Nav, Footer, Seo) using **Paraglide JS v2**. Other marketing pages and the reader follow the same rules and are listed as follow-on. Implemented detail lives in code; this doc does not restate it.

This doc is the UI-language counterpart to [`quran.md`](./quran.md). The two never overlap: **UI chrome language** (here) and **translation content language** (`quran.md` §5 `/t/<lang>`) are orthogonal axes a user mixes freely.

---

# Part 1 — settled

## Hard rules

- **Two languages, never confused.** UI chrome lang (nav, buttons, prose, SEO copy) ≠ translation content lang (`/t/<lang>/<translator>`). A reader can be UI-Arabic + English-translation + stacked Urdu. Each axis independent.
- **Marketing pages: locale is a server dimension.** Locale lives in the URL and the page is **SSG-prerendered per locale**. The matrix is small (`marketing pages × locales`) and bounded — this is the *only* place locale enters a server/cache key.
- **Reader/app pages: locale is client-only.** UI chrome lang is resolved post-hydration and **never** enters a server cache key or SSR route. Carries forward the rule in [`quran.md`](./quran.md) §7 / the rendering-tiers decision: server stores single-source immutable units; client owns every user-combinatorial choice.
- **Base locale (`en`) is unprefixed.** `/`, `/about` keep their existing URLs — the site is live and indexed. Other locales are path-prefixed (`/ar/`, `/ar/about`). Protects existing URL equity; no mass 301s.
- **No machine translation shipped.** Every locale is hand-written and reviewed. MT may draft, never publish.
- **Strings live in `messages/<locale>.json`, not in components.** After migration, no user-facing English literal remains in a `.svelte` / `site.ts` string field. Brand name ("EasyQuran"), email addresses, and numeric/structural tokens are not strings.

## Stack — Paraglide JS v2

Decision: **Paraglide JS v2** (`@inlang/paraglide-js`, Vite plugin). It is SvelteKit's officially recommended i18n.

- **Compiler-based** — messages compile to tree-shakable functions at build time. No runtime catalog, no async waterfall, smallest bundle. Suits SSG.
- **Type-safe** message functions; missing-key is a build/type error.
- **First-class SSR/SSG** — locale resolved server-side per request/prerender, so `<html lang/dir>`, SEO, and structured data are correct in the static HTML.
- **Strategy `['url', 'cookie', 'baseLocale']`** — locale from path, remembered via cookie, falling back to base. URL is source of truth so prerendered pages are stable and shareable.

Rejected: `typesafe-i18n` (maintainer deceased — do not start new work on it); `sveltekit-i18n` / `svelte-i18n` (runtime catalogs, weaker types, no SSG story); Intlayer / Better-i18n (external CDN/Git service — clashes with self-hosted Dokploy).

## Locales

Starter set: **`en` (base) + `ar`**. Arabic is the natural first secondary for a Qur'an reader and forces the RTL pass early. Adding a locale = one entry in `project.inlang` + one `messages/<locale>.json` + one `entries()`/sitemap fan-out. No code changes elsewhere. **Decision pending: final locale list** (likely adds `ur`, `id`, `fr`).

# Part 2 — the work (landing page first)

Ordered by dependency. §1–§3 are one-time setup and unblock §4. §5 is the SEO/RTL finish. §6 lists follow-on.

## 1. Install + project scaffold

**Approach:** add `@inlang/paraglide-js`, create `project.inlang` at the web root with `baseLocale: "en"`, `locales: ["en","ar"]`, and message-output config. Generated runtime lands in `src/lib/paraglide/` (alias `$paraglide`). Add the path alias to `tsconfig.json`.

Wire the Vite plugin into the existing `lazyPlugins` array in `vite.config.ts` — note `vite-plus` wraps SvelteKit, and `paraglideVitePlugin` runs `enforce: "pre"` so order in the array does not matter:

```ts
// vite.config.ts — inside lazyPlugins(() => [ ... ])
paraglideVitePlugin({
  project: "./project.inlang",
  outdir: "./src/lib/paraglide",
  strategy: ["url", "cookie", "baseLocale"],
}),
```

**Done when:** `pnpm dev` boots with Paraglide, `$paraglide` resolves, and a throwaway `m.hello()` round-trips en/ar.

## 2. Document language + direction

`app.html` ships `<html lang="en" …>` as a static literal. For SSG each prerendered page must carry its own `lang`/`dir`.

**Approach:** set `<html lang>` / `dir` per locale at render from the Paraglide runtime (`getLocale()`, `getTextDirection()`), via the Paraglide SvelteKit adapter's document-root recipe (it exposes locale on `event.locals.paraglide`). This needs a `src/hooks.server.ts` — **none exists today** — that runs Paraglide's server middleware so locale is resolved before prerender. Exact attribute wiring per current adapter docs; the invariant is: every emitted HTML file has correct `lang`/`dir` for its locale, in the static source.

**Done when:** `/ar/` HTML ships `<html lang="ar" dir="rtl">`; `/` ships `lang="en" dir="ltr"`; verified in prerendered output, not just dev.

## 3. Route shape — unprefixed base

**Decision:** base locale keeps existing URLs; other locales prefixed. One component tree via an **optional `[locale]?`** segment so `/` and `/ar/` share code:

```
src/routes/(marketing)/[locale]?/+page.svelte        ← landing, all locales
src/routes/(marketing)/[locale]?/+layout.ts          ← prerender + entries()
src/routes/(marketing)/[locale]?/about/+page.svelte  ← follow-on, same pattern
```

`+layout.ts`:

```ts
export const prerender = true;
import { locales } from "$paraglide/runtime.js";
export const entries = () => [{ locale: undefined }, ...locales.filter((l) => l !== "en").map((locale) => ({ locale }))];
```

`locale === undefined` ⇒ base (`en`). **Confirm Paraglide v2's no-prefix-for-base-locale strategy setting** at setup; if the optional-segment + strategy combination does not fall out cleanly, fall back to two thin route trees (existing `(marketing)/` for `en`, `[locale]/(marketing)/` mirror for the rest) that import shared page components. Either keeps components single-sourced.

**Done when:** `/` and `/ar/` both render the landing with correct locale; `/de/` 404s (not in locales); both are prerendered artifacts.

## 4. Extract landing + chrome strings

The localizable surface for the landing (inventoried against current code):

| Source | Strings |
|---|---|
| `(marketing)/+page.svelte` | h1, subtitle, "Free forever…" badge, "Today"/"On the way" eyebrows, 2 section heads + intros, 4 value cards (title+body), "Coming" tag, 4 roadmap cards (title+body), "Start reading" / "Why we built it" CTAs |
| `nav/Nav.svelte` | "Open the app" (×2), aria-labels (Primary, Offline, Toggle theme, Menu, Close menu, Mobile) |
| `config/site.ts` | `SITE.tagline`, `SITE.footerBlurb`, `NAV_LINKS[].label`, `MARKETING_PAGES[].label`, `PAGE_META[].title/description` |
| `seo/Seo.svelte` | (handled in §5) |

**Approach:** move these into `messages/en.json` + `messages/ar.json` under a `landing.*`, `nav.*`, `site.*` namespace. Replace literals with message calls — `m.landing_hero_title()`, `m.nav_open_app()`, etc. For `site.ts` data tables (`NAV_LINKS`, `PAGE_META`), keep the table structural and look up the label by message key (e.g. `label` becomes a key id, resolved through `m` at render) so the data file stays locale-free. `site.ts` brand/URL/owner fields stay literal — they are not UI copy.

**Done when:** no user-facing English literal remains in the landing, Nav, or the `site.ts` UI fields; `en` output is byte-identical in copy to today; `ar` reads as natural Arabic.

## 5. SEO + RTL pass

**SEO — parameterize `Seo.svelte`** (today's literals: `inLanguage: "en"`, `og:locale: "en_US"`):

- `inLanguage` and `og:locale` ← current locale (map `ar → ar_AR`, etc.).
- `canonical` ← localized URL via `localizeHref`.
- **hreflang alternates** for every locale + `x-default` → base URL.
- `PAGE_META` titles/descriptions resolve through messages, so `<title>`/`og:title`/JSON-LD localize.
- Sitemap (`src/routes/sitemap.xml`) fans out every marketing URL × locale.

**RTL — Arabic full-page RTL.** The app already does RTL for Qur'an content spans; marketing chrome has not been audited for bidirectional layout.

- Audit `(marketing)` + Nav/Footer for physical properties (`ml-/mr-`, `left/right`, `text-left`) → switch to logical (`ms-/me-`, `start/end`, `text-start`). Tailwind v4 ships logical utilities.
- Verify nav order, icon positions, badge layout, mobile drawer under `dir="rtl"`.

**Done when:** `/ar/` passes a manual RTL review (no mirrored-from-LTR glitches), Lighthouse SEO green, hreflang valid, sitemap includes all locales.

## 6. Follow-on (not in this milestone)

- `about`, `faq`, `contact`, `privacy`, `terms` — same pattern. `content.ts` (`FAQS`, `PRIVACY_SECTIONS`, `TERMS_SECTIONS`, `ABOUT_STATS`) becomes message-keyed, not string arrays.
- **Reader/app UI chrome** — client-only Paraglide (core message fns, locale from a client store, **not** the URL strategy, **not** any server key). Separate milestone; do not let the marketing URL strategy touch `/app`.
- Locale switcher in Nav — `localizeHref` + `data-sveltekit-reload` (full reload is required for per-locale SSG).
- Translation workflow — hand-edit JSON for now; consider the inlang editor/Fink only if volume demands.
