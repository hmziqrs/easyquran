# EasyQuran — UI i18n delivery plan

Single source of truth for UI internationalization. This is an implementation plan, not an index.

First milestone: localize landing page (`/`) plus its marketing chrome and SEO. The first published locale pair is `/` (English) and `/ar/` (Arabic). Other marketing pages remain English-only until their body copy, metadata, links, text representations, and tests are ready.

Second milestone: localize reader chrome and make every reader URL explicitly UI-locale-prefixed, including English: `/en/app/**` and `/ar/app/**`. The first two UI locales are `en` and `ar`.

This document governs **UI language** only: navigation, controls, marketing copy, metadata, and accessibility text. It is separate from Qur'an **translation content** (`/{ui}/app/t/<contentLang>/<translator>` publicly, `/app/t/<contentLang>/<translator>` after de-localization); users may combine either UI locale with any translation-content locale.

---

## 1. Non-negotiable boundaries

- UI locale and Qur'an translation-content locale are independent axes. Never infer one from the other.
- Marketing locale is URL-owned and SSG-prerendered. `/` is English; `/ar/` is Arabic. Each published locale-page pair has one stable, shareable document URL.
- Reader UI locale is URL-owned: every canonical reader path starts `/{UiLocale}/app`. Do not emit a reader link without that prefix after reader-localization rollout.
- UI locale is frontend-web-only. It may select compiled UI copy, public path, reader HTML cache variant, and static reader artifact; no Rust endpoint, request header, query parameter, database column, migration, Quran catalogue lookup, or translation-source selection may receive it. Use `UiLocale`, never `lang`, `languageCode`, or `TranslationId`.
- Reader delivery keeps its source-content split: Arabic-source reader pages prerender once per supported UI locale; translated-source reader pages remain SSR with their 7-day disk cache, now safely partitioned by bounded `UiLocale`. No Quran byte, source identity, source selection, or backend request varies by UI locale.
- The routing allowlist accepts published localized marketing paths and the complete reader grammar only. Unsupported locales (for example `/de/app`), unpublished marketing pairs (for example `/ar/about` in the landing milestone), and locale prefixes outside those two surfaces must 404.
- Marketing English remains unprefixed. Do not migrate indexed English marketing URLs or add a bulk redirect. Reader English is deliberately prefixed as `/en/app/**`, so a locale switch never changes the canonical reader URL shape.
- No machine translation ships. Every catalog change is reviewed by a fluent human. MT may assist a draft outside the repository only.
- Qur'an text is not UI copy. Preserve the footer quotation verbatim, mark it `lang="ar" dir="rtl"`, and do not move it into a UI catalog.
- Message calls run at component/render time or inside a request-scoped function. Never evaluate `m.*()` in module-level config, a static object initializer, or another server-global context.
- Generated Paraglide output is build artefact, not source. Edit `project.inlang/` and `messages/`; do not edit `src/lib/paraglide/`.

| Surface | Language/direction owner | Locale source |
|---|---|---|
| Marketing UI | Current UI locale; document `%lang%`/`%dir%` | Published marketing URL |
| Reader UI chrome | Current UI locale; nested reader-shell `lang`/`dir` | `/{UiLocale}/app/**` |
| Qur'an Arabic | Immutable Qur'an text; `lang="ar" dir="rtl"`; Qur'an font | Arabic source, never UI locale |
| Qur'an translation content | Source language/direction on its own content boundary | Translation source ID/route, never UI locale |

### Locale persistence

Marketing uses URL as the sole locale source: `strategy: ["url", "baseLocale"]`.

Do **not** add `cookie`, `localStorage`, or `preferredLanguage` to this strategy. A cookie could make `/` render Arabic, make its canonical URL lie, and send a cookie on every reader request; this repository deliberately bypasses shared translated-reader HTML caching for cookie-bearing requests. A locale switch is a link to a locale URL, not a remembered server preference.

Reader UI locale is canonical in its URL. Do not add a cookie, `localStorage`, `preferredLanguage`, or Accept-Language override; the URL is always authoritative. For the first release, a valid legacy `/app/**` request sends a `307` with `Cache-Control: no-store` to its exact `/en/app/**` equivalent, preserving query and fragment. It never renders reader HTML, enters the translated-reader disk cache, or appears in new navigation. This reversible alias avoids duplicate canonical shells during rollout; promote it to a permanent redirect or remove it only after the offline-cache and rollback window are approved.

## 2. Chosen stack and source layout

Use Paraglide JS v2 (`@inlang/paraglide-js`) through its Vite plugin. It compiles typed message functions, supports URL localization, and isolates locale per SSR request. Pin all i18n packages in `pnpm-lock.yaml`; no runtime catalog fetch or translation SaaS is allowed.

`web/` owns this layout:

```text
project.inlang/
  settings.json                 # base locale, supported locales, local plugins
messages/
  en.json                       # reviewed English source copy
  ar.json                       # reviewed Arabic copy; same keys and parameters
src/lib/i18n/
  locales.ts                    # UiLocale registry, path parsers, direction metadata
  marketing.ts                  # canonical marketing paths, publication matrix, URL helpers
  reader.ts                     # reader UI-path composition; preserves source route context
  marketing-copy.ts             # request-time adapters for Nav/Footer/MarketingSeo
  reader-copy.ts                # request-time adapters for reader chrome only
src/lib/paraglide/              # generated and gitignored
```

`project.inlang` is a **directory**, not a single config file. Configure its message-format plugin to read `./messages/{locale}.json`. Keep any build-required plugin as a pinned local `devDependency` referenced from `node_modules`; a production build must not need a CDN/Git fetch. Add the optional editor matcher only when its locally pinned tool is actually adopted.

Set `outdir: "./src/lib/paraglide"` and `emitTsDeclarations: true` in `paraglideVitePlugin`. `$lib/paraglide/...` is already resolvable in SvelteKit; do not add a second `$paraglide` alias. Place the plugin before `sveltekit()` in the existing `lazyPlugins` array.

The Vite plugin handles dev/HMR and builds, but `pnpm check`, `pnpm test`, and lint can run without Vite first. Add one `i18n:compile` script that invokes the installed Paraglide CLI with `--emit-ts-declarations`; run it in `precheck`, `pretest`, `prelint`, and `prebuild`. This prevents a clean checkout from failing on missing generated imports.

### Locale metadata

Keep behaviour metadata in one typed `UI_LOCALES` registry. Each entry carries:

- BCP-47 locale (`en`, `ar`);
- endonym for the switcher;
- text direction; and
- Open Graph locale (`en_US`, `ar_SA`). `ar_AR` is not used.

The registry, not the Quran translation catalogue, drives switcher options, localized sitemap fan-out, hreflang tags, and prerender discovery. A second typed `MARKETING_PUBLICATIONS` matrix owns which `{ pageId, locale }` pairs are live: every existing page has `en`; only `home` has `ar` initially. Reader publication is simpler: every supported `UiLocale` has every reader path. Adding a locale requires its registry entry, `project.inlang/settings.json` entry, complete reviewed message catalog, language/RTL review, the appropriate publication entries, static-artifact capacity review, and the normal test matrix. No route or sitemap code fork.

## 3. Routing, SSR, and prerendering

Keep the existing SvelteKit marketing tree (`(marketing)/+page.svelte`, `(marketing)/about`, etc.) and reader tree (`(application)/app/**`). Do **not** duplicate components. The `/app/**` grammar is an internal SvelteKit route target, not a public reader URL after rollout. Paraglide de-localizes a valid `/{ui}/app/**` request to that internal target; `localizeHref()` creates the public locale URL.

Generate explicit Paraglide `urlPatterns` from `MARKETING_PUBLICATIONS`, with `/ → en` and `/ar/ → ar` initially. Add the reader pattern below, with the more-specific localized forms before any less-specific form:

```ts
{
  pattern: "/app/:path(.*)?",
  localized: [
    ["en", "/en/app/:path(.*)?"],
    ["ar", "/ar/app/:path(.*)?"],
  ],
}
```

Do not add a default `/:path(.*)?` catch-all: it would treat unpublished or non-reader routes as localized and defeat the allowlist. `localizeHref()` is allowed only for a known matching canonical pattern. When a marketing page is published in Arabic, add its publication entry; the generated pattern maps it to its existing canonical route. Do not hand-build locale prefixes.

Prerender must traverse each published localized URL through the same SvelteKit/Paraglide request path used in production and resolve `UiLocale` explicitly during SSG. The reader integration must prove route-local locale binding before migration: generated `/ar/app/<surah>` contains Arabic UI messages and a reader-shell `lang="ar" dir="rtl"`; generated `/en/app/<surah>` contains English UI messages. The Arabic-source document root remains `lang="ar" dir="rtl"` in both variants. Do not rely on a process-global locale or merely assert that output route files exist.

### Required integration

1. Replace static `<html lang="en">` in `web/src/app.html` with `%lang%` and `%dir%` placeholders. One composed root-HTML transform must replace both placeholders on **every** document: default `en/ltr`; marketing overrides both from `UiLocale`; reader routes retain content-source document language/direction. Reader UI direction belongs on the reader shell, never on translation-content spans or by changing source-text semantics. No placeholder may survive an emitted or cached document.
2. Add `web/src/hooks.ts` with SvelteKit `reroute`. First use `deLocalizeUrl()` to derive a canonical candidate; then validate the tuple of raw localized URL and candidate against either `MARKETING_PUBLICATIONS` or the complete reader route grammar. Reroute only a valid published tuple. Return the original pathname for every other route, so `/ar/account` and malformed `/ar/app/...` cannot become another route.
3. Extend the existing `web/src/hooks.server.ts`; it already owns security headers, HTML-language substitution for reader content, and translated-reader disk caching. Do not replace it or create a second `handle`.
4. On an allowlisted marketing **or localized-reader** document request, call `paraglideMiddleware(event.request, ...)`, assign its localized request to `event.request`, and combine its transforms with the existing resolver. Keep AsyncLocalStorage enabled. The closure is the sole server-side source of `UiLocale`; it passes that bounded value to reader copy and the translated-reader HTML cache only, never to the Rust API. Keep the public request URL available for locale resolution while `reroute` selects the internal SvelteKit route.
5. Refactor the existing hook around one final response path: a normal marketing response, localized-reader response, cache response, and any Paraglide redirect all pass through `applyHeaders()` exactly once. Paraglide may short-circuit with a redirect; that response must retain CSP/security/cache policy. Preserve the translated-reader cache branch and its response headers unchanged except for the bounded `UiLocale` cache partition.
6. For all other paths, run the present hook unchanged. API, assets, offline files, text endpoints, and auth/account/health routes do not use i18n middleware. Before the reader cache branch, validate a legacy `/app/**` request against the same reader grammar and issue its temporary redirect to `/en/app/**`; it does not render a fixed-English legacy document.

The shared marketing helper accepts a page ID and supplies `marketingHref(pageId, locale)` via `localizeHref()` only when that page-locale pair is published; otherwise it returns `null`. It must reject reader, product, account, auth, API, asset, and text-variant routes.

The reader helper is a separate boundary: `readerHrefFor(uiLocale, quranHref)`. `quranHref` must already come from `surahPathFor`, `surahLocalPagePathFor`, `surahAyahPathFor`, `globalPagePathFor`, or `juzPathFor` with `ctx` from `surahRouteContext(sourceId)` or `routeContextFromParams(page.params)`. It accepts only a supported `UiLocale` and an origin-relative canonical `/app` reader href; reject absolute/cross-origin, protocol-relative, non-reader, and malformed input. The helper localizes that returned canonical reader path without parsing/reconstructing Quran source segments. It returns `/en/app/...` or `/ar/app/...`, preserving `/t/<lang>/<translator>` and query/fragment. It is the only allowed reader UI-prefix operation; no component hand-builds `/{locale}/app` or `/app` strings.

### Links and static discovery

- Use `marketingHref()` only for links between marketing pages. Marketing CTAs use `readerHomeHrefFor(currentUiLocale)`, not a raw `/app` literal. Account/auth links remain their existing routes. Every reader navigation call keeps its existing `surah*For(ctx, ...)` family, then passes the result to `readerHrefFor(currentUiLocale, ...)`; it never uses the marketing localizer. Do not link an Arabic page to an unpublished Arabic marketing destination or silently switch it to English; hide that destination until its locale-page pair is published.
- Add `data-sveltekit-reload` to every cross-locale link. The switcher must preserve query and fragment, show native locale names with their own `lang`, and set `aria-current` on the active locale. A full navigation keeps URL, document `lang`/`dir`, SSR locale, and client runtime synchronized.
- Add a real, visible locale switcher to marketing Nav, limited by `marketingHref()` and the current page's published alternatives. Add the same control to reader Nav: it maps the current canonical Quran path through `readerHrefFor(targetUiLocale, ...)`, retaining any translation-source context. The marketing switcher supplies crawler discovery for its bounded publication matrix.
- Preserve the existing Arabic-source reader `entries()` enumeration. Add a build-only `ReaderPrerenderLinks` container with the HTML `hidden` attribute, generated from every existing Arabic-source entry × `UiLocale` through `readerHrefFor()`. It is not an interactive or accessibility-tree navigation surface; it is deterministic prerender discovery. Assert its 2,592 URL set and remove it only if an equivalent explicit SvelteKit public-URL prerender API is adopted.
- Use the URL returned by the helper consistently for canonical and sitemap output; do not append or remove a slash manually. This avoids creating a second canonical form while the project keeps `trailingSlash = "ignore"`.

### Reader public grammar

`UiLocale` comes before `/app`; Quran translation-content segments keep their current positions after it:

```text
/{ui}/app
/{ui}/app/{surah}
/{ui}/app/{surah}/page/{localPage}
/{ui}/app/page/{globalPage}
/{ui}/app/juz
/{ui}/app/juz/{juz}
/{ui}/app/{surah}/t/{contentLang}/{translator}
/{ui}/app/{surah}/t/{contentLang}/{translator}/page/{localPage}
/{ui}/app/t/{contentLang}/{translator}/page/{globalPage}
/{ui}/app/t/{contentLang}/{translator}/juz/{juz}
```

`ui` is `en` or `ar`; `contentLang` and `translator` remain the immutable translation-source selector. Reader UI locale changes no source selection. Arabic-source output is SSG for both UI locales: current route count is `2 × (114 surah roots + 548 extra local pages + 604 global pages + 30 juz) = 2,592` reader documents, plus the bounded entry routes. Translated-source paths are never prerendered; `UiLocale` doubles rendered variants, not Quran source variants.

These are public URL forms. `reroute` maps each syntactically valid one to the existing internal `/app/**` route with the exact same Quran-source suffix. Route components, loaders, and Rust calls receive the existing source context, not a `UiLocale` route parameter. The prefix validator rejects encoded separators, dot segments, duplicate separators, unsupported UI locales, and shapes outside this table.

Extract one pure server-side `parseReaderRoute(routeId, params)` and use it for the legacy redirect, translated-reader cache key, and route loads. It validates the resolved internal shape, surah slug, local/global-page and juz bounds from `QURAN_DATA`, and translation ID presence in the baked catalogue. It returns a validated discriminated union—`home`, Arabic-source route, or translated-source `{ sourceId, kind, index, localPage? }`—or `null`; only the translated variant can make a disk-cache key. It neither accepts nor derives `UiLocale`, and it never asks remote catalogue metadata to select an ID. Run it before a disk-cache lookup and before rendering, so invalid suffixes cannot probe cache keys or produce a cached error. Locale parsing must not turn an arbitrary `/{ui}/app/**` string into a reader route.

## 4. Copy model and component seams

Message keys describe meaning, not page markup. Use flat compiler-friendly keys such as `landing_hero_title` and `nav_open_panel`; keep arguments named and identical across locales. Use ICU plural/select variants for quantities or grammar, `Intl` formatting for dates/numbers, and component composition for links, emphasis, icons, and any rich markup. Do not store HTML, Tailwind classes, URLs, icon IDs, or trusted HTML in catalogs.

`messages/en.json` is the reviewed English baseline, not an automatic fallback. Every shipped locale must contain the same key set, parameter signatures, plural branches, and required select branches. Missing, unknown, or structurally incompatible messages fail compile/test; production does not silently fall back to English.

Paraglide 2.23 uses inlang SDK v2.10, which ignores legacy `messageLintRule` modules. Do not install the deprecated missing-translation package. Implement `pnpm i18n:check` as a local deterministic catalog check: every configured domain must exist for every locale; merged keys, value shapes, parameters, plural/select branches, and required variants must match; duplicate cross-domain keys, empty messages, and malformed JSON fail. Run it before `check`, `lint`, `test`, and `build`; compilation alone is not sufficient coverage validation. Revisit native lint integration only when inlang ships its replacement validation API.

Message policy:

- Use static typed message calls through exhaustive page-ID resolvers; never use `m[key]` where `key: string`.
- Interpolate only typed scalar values. Do not concatenate translated fragments.
- Never feed catalog content to `{@html}`. Rich linked sentences stay out of this milestone and are composed from safe elements.
- Arabic plural/select fixtures cover `zero`, `one`, `two`, `few`, `many`, and `other` when a message uses quantity.
- Format dates, numbers, and relative time with `Intl` and the resolved UI locale, not browser-default `toLocaleString()`. Gregorian/Hijri presentation, device timezone, and digit display are explicit future reader decisions; route IDs and source IDs keep ASCII digits.
- Landing/card view models keep stable structural IDs. Do not key an `{#each}` block with translated copy.

### Structural data stays structural

Refactor `web/src/lib/config/site.ts` so it contains identity and route structure only: site name/domain/URLs, page IDs, canonical marketing paths, and navigation membership. Its current `tagline`, `footerBlurb`, labels, and marketing metadata are copy and move to messages. `renderLlmsIndex()` and the top-level `.md`/`.txt` endpoints still require static English descriptions: give them an explicit base-English copy adapter, evaluated only at request/render time, rather than calling request-scoped `m` from a module global.

Resolve labels at the rendering boundary using a page ID or message-key adapter. Do not import `m` into a module-level `NAV_LINKS`/`PAGE_META` object; SSR would freeze or leak a locale. Keep content-source metadata explicit; reader UI labels resolve in the reader request/client context of `UiLocale`.

### Scope inventory

The first milestone migrates all user-visible strings in these **marketing instances**:

| Surface | Required copy |
|---|---|
| `(marketing)/+page.svelte` | badge, hero, both CTAs, section eyebrows/headings/intros, four value cards, roadmap tag/cards |
| `Nav.svelte` when rendered by marketing layout | landmark/dialog/button labels, offline state text, search/account/panel titles, appearance/theme controls, locale-switcher labels |
| `Footer.svelte` | blurb, column headings, product/legal links, social label, attribution prose; excludes brand/URLs/year and Qur'an quotation |
| `Tweaks.svelte` when rendered by marketing layout | all headings, theme/surface/accent controls, labels, descriptions, ARIA/title text, and live status text |
| `Brand.svelte` when rendered by marketing layout | accessible home label; brand spelling remains structural |
| marketing SEO | title, description, Open Graph/Twitter image alt text, breadcrumbs, page JSON-LD, hreflang labels where applicable |
| shared/global layout | factor the skip link into route-specific layouts so marketing gets localized copy and app remains explicitly English; remove the hard-coded `WebSite.inLanguage: "en"` from the shared graph; page-language graph belongs to marketing SEO |

`Nav.svelte` is also mounted under `/app`. Do not make it import Paraglide messages directly. Give the shared structural component resolved label props (or use separate thin `MarketingNav`/`ReaderNav` wrappers). Marketing and reader resolve labels in their own request/client contexts. Apply the same separation to generic `Seo.svelte`: add a marketing wrapper/explicit props for localized canonical and metadata rather than changing Qur'an-content SEO semantics.

`Brand.svelte` likewise receives `homeHref` and `homeLabel`: marketing Arabic receives `/ar/`; reader receives `readerHomeHrefFor(currentUiLocale)`; each receives localized accessible copy.

The old blanket rule “no English literal anywhere in `.svelte` or `site.ts`” is too broad for a landing-page milestone. Enforce it on named migrated surfaces, with narrowly documented structural exceptions. Unshipped marketing pages remain follow-on work, not hidden partial localization.

### Reader UI seam

Second milestone migrates every reader-chrome string in `(application)/app`: shared Nav/Tweaks/Brand, reader layout, Sidebar, Results, RangeReader, Surah reader/page controls, verse tools, offline/download/update status, reader preferences, empty/error/loading states, dialogs, visible labels, titles, ARIA text, and live-region text. Start with a checked inventory test; do not rely on an incomplete hand list.

Reader components receive a typed `ReaderUiCopy` view model or call messages only inside the current Svelte render/request context. The client derives `UiLocale` from the canonical public reader URL; SSR receives the same value from `paraglideMiddleware`; hydration must agree. Legacy `/app/**` redirects before a reader component is created.

The reader shell carries `lang={UiLocale}` and `dir={uiDirection}`. Quran source boundaries stay explicit: Arabic text remains `lang="ar" dir="rtl"` with its Quran font; translation text receives its catalogue `lang` and direction, never `UiLocale`, and retains `dir="auto"` only where mixed script requires it. Do not localize surah names, ayah text, verse markers, source IDs, translator names, or downloaded Quran metadata into UI catalogs.

## 5. SEO and non-HTML representations

`MarketingSeo` owns locale-aware head output. For each indexable marketing page it must emit:

- localized `<title>`, description, Open Graph/Twitter fields, and page JSON-LD;
- a self canonical URL from `marketingHref(canonicalPath, currentLocale)`;
- one hreflang alternate for every published locale of this page, including self, plus `x-default` to this page's English publication; and
- correct `inLanguage` and registry-derived Open Graph locale.

Keep the global organization identity graph language-neutral, or move its localized `WebSite` node into the marketing wrapper. Do not leave a global `inLanguage: "en"` node on Arabic pages.

`web/src/routes/sitemap.xml/+server.ts` currently mixes marketing pages with Qur'an-content translation alternates. Extend it with a separate UI-locale group sourced only from `UI_LOCALES` and `MARKETING_PUBLICATIONS`. Never advertise an unpublished marketing pair. Never use the Quran translation list for UI marketing sitemap/hreflang data.

Reader UI locale is not Quran translation-content language. Reader canonical tags and sitemap entries use the `en` reader-UI form (`/en/app/**`) once reader URLs ship. The Arabic UI form (`/ar/app/**`) self-identifies its UI shell but canonicalizes to its equivalent English-UI reader URL; it is not an extra Quran-content `hreflang` alternate or sitemap entry. Existing Quran-content alternates keep mapping Arabic source and translation source contexts, now all through `readerHrefFor("en", ...)`; they never equate `UiLocale` with `contentLang`.

The current `.md`/`.txt` representation routes are top-level only. Do not emit a localized text-alternate URL until an endpoint actually serves it. First milestone sets `includeTextVariants={false}` for every non-base marketing document; the follow-on must add nested localized representations and test them before restoring those links. Reader UI locale does not create text-variant paths.

## 6. RTL, language, and accessibility

Arabic means full RTL UI chrome, not only Arabic copy. Review `(marketing)`, reader shell, Nav, Footer, Tweaks, shared layout controls, and focus states under `dir="rtl"`.

- Replace physical positioning/margins/alignment (`left/right`, `ml/mr`, `text-left/right`, `border-l/r`, right-anchored drawer transitions) with logical properties/utilities where direction should mirror. Keep intentionally physical values documented.
- Verify flex order, icon placement, chevrons/arrows, reader pagination controls, drawer origin, mobile focus trap, skip link, keyboard order, virtualized sidebar direction, and restored focus after closing the panel.
- Give Arabic UI copy an intentional readable UI font stack. Qur'an glyphs keep their existing Quran-specific font and `lang="ar" dir="rtl"`; UI typography and Quran typography are separate choices.
- Keep Latin product names, URLs, emails, code, and numeric IDs isolated with `dir="ltr"` when their surrounding RTL context would reorder them. Never localize route IDs, Quran source IDs, ayah numbers, or database identities.
- Use `lang` on passages that differ from document language, localize ARIA/title/visible label together, and retain icon-only controls' accessible names.
- UI dates, numbers, and relative time use `Intl` with `UiLocale`; reader navigation URLs, Quran source IDs, Quran page/juz numbers, and verse marker semantics stay ASCII/source-defined. Gregorian/Hijri presentation and device-timezone policy are explicit reader-product decisions before exposing a localized date/calendar feature.

2. **Create the marketing boundary.** Add locale/path metadata, marketing-only URL helper, `hooks.ts` reroute guard, scoped server middleware integration, and `%lang%`/`%dir%`. Regression-test the existing `hooks.server.ts` cache/header behaviour before touching copy.

4. **Migrate landing and footer copy.** Port the full inventory to reviewed English and Arabic catalogs. Preserve English wording; compare rendered text/content rather than byte-identical HTML, because head and document attributes intentionally change.
5. **Finish SEO and SSG discovery.** Add localized canonical/alternate metadata, sitemap fan-out, and prerender links. Prevent invalid text-variant alternates.
6. **Add reader locale grammar.** Implement `UiLocale`, reader URL patterns, `readerHrefFor`, prefix and semantic route validation, the temporary legacy `/app/** → /en/app/**` redirect, and route-aware reader navigation migrations. Update the navigation guard so every reader link is `readerHrefFor(ui, surah*For(ctx, ...))` or its range equivalent.
7. **Preserve reader delivery.** Prerender Arabic-source reader routes across `UiLocale`; leave every translated route SSR. 9. **Finish reader SEO, offline, and RTL.** Canonicalize reader UI variants correctly, update reader sitemap generation to the `en` canonical UI form, verify service-worker path isolation, remove inappropriate physical CSS, and test desktop/mobile keyboard and screen-reader names in both directions.

## 8. Verification matrix

Automated coverage must include:

- catalog key/parameter/variant parity; malformed or missing Arabic copy fails;
- `marketingHref()`, `readerHrefFor()`, and reroute allowlist: published/unpublished marketing pairs; every reader shape; `en`/`ar`; unknown locale; encoded separator/dot-segment/duplicate-separator rejection; malformed prefixed path; legacy `/app/**` redirect; preserved query/fragment; and no hand-built prefix;
- reader navigation guard: each UI-prefixed reader link wraps `surah*For(ctx, ...)`, `globalPagePathFor(ctx, ...)`, or `juzPathFor(ctx, ...)`; translation context remains exactly `/t/<contentLang>/<translator>` after UI switch, search result, sidebar, pagination, ayah deep link, and resume;
- hook regression: non-marketing requests retain today's headers; reader document content language stays source-derived; reader shell language/direction stays UI-derived; translated reader cache key/hit/cookie-bypass behaviour is unchanged except for bounded `UiLocale`; normal and redirect outcomes apply headers once; and no `%lang%`/`%dir%` token survives;
- `/` with an arbitrary locale cookie or `Accept-Language: ar` still emits English; `/en/app/**` and `/ar/app/**` always retain their URL-selected UI locale under the same inputs; no locale cookie is written; no locale `Set-Cookie` or `Vary: Accept-Language` is emitted;

## 9. Review and operations

Each Arabic catalog PR names a fluent Arabic reviewer and includes the generated-artifact checks, `/` and `/ar/` smoke result, sitemap diff, and RTL evidence. Do not collect raw headers, page text, or user IDs for localization analytics. If metrics are later added, keep them consent-gated, finite, aggregate locale counts only, and separate from Qur'an-content selection.

Marketing and reader navigation cache identity is pathname only. No i18n-specific CDN TTL, cookie/header variation, or Quran-data cache variation is introduced; retain the deployed `no-cache` HTML policy. Translated-reader disk HTML additionally has a bounded `UiLocale` partition because the HTML shell differs. Rollback is a normal application rollback plus invalidation of affected `/ar...` and `/{ui}/app...` public paths and their service-worker page entries; remove stale legacy `/app/**` page entries before enabling its redirect. Verify `/`, `/ar/`, `/en/app/al-fatihah`, `/ar/app/al-fatihah`, one translated reader route in each UI locale, the legacy redirect, and `sitemap.xml` after every deploy or rollback.

## 10. Follow-on and decisions

After this milestone, localize `about`, `faq`, `contact`, `privacy`, and `terms` through the same structural page registry and marketing wrapper. Convert their `content.ts` arrays to message-keyed data only when their page enters scope.

Reader/app chrome and canonical `/{ui}/app/**` paths are the second milestone specified here. Adding new UI locales after `en`/`ar` requires capacity review because Arabic-source reader SSG scales linearly by locale, while translated-reader SSR HTML cache variants scale by locale. It must never alter Quran data, source selection, translation identities, or Rust/backend contracts.

Remaining product decisions:

1. Final locale order after `en` and `ar` (candidates: `ur`, `id`, `fr`).
2. Translation contributor workflow and review ownership.
3. Whether localized `.md`/`.txt` marketing representations are worth maintaining.

## Out of scope

- Machine-translated publishing.
- Localizing Qur'an text or changing Quran databases.
- Changing Quran data, source selection, translation identities, or Rust/backend delivery to support UI locale.
- Locale cookies, Accept-Language redirects, automatic language detection, and app-wide client locale persistence.
