# Audit — Web Cache API + OPFS

> Status: audit findings, verified against source (commit `ea5fc28` on master, 2026-08-13); re-verified in pass 2 (live sources) and pass 3 (source + built adapter output at `1d5ead5`).
> Architecture verdict: **implemented properly** — hard rules intact, core algorithms correct; defects are localized medium/low cache-efficiency and state-reporting gaps. No critical or high risk to Quran data integrity.
> Only claims re-proved from code + MDN are recorded. Every item carries file:line evidence.

Eight dimensions reviewed (`cache-routing`, `cache-lifecycle`, `cache-eviction`, `cache-isolation`, `opfs-crash-safety`, `opfs-pointer-integrity`, `opfs-retention`, `opfs-storage-fallback`); each actionable finding was adversarially verified. Two claims were REFUTED (one at the end, plus L10 in the re-verification). No critical/high finding survived. Current tally: **2 medium (M1, M2), 11 low (L1–L9, L11, L12), 1 info (I1)**; L10 refuted.

## Strengths

- **Hard rule intact across all eight dimensions.** No SHA-256/content-hash over Quran data anywhere — `verifyBytes` (`web/src/lib/workers/download.ts:24-33`) is size-only (`buf.byteLength !== spec.sizeBytes`); every cache/meta key is id-derived (`data:` prefix, `${tag}:${id}`, `${id}.sqlite`, `packId`), never hash-derived. Grep of `service-worker.ts`, `lib/workers/`, `lib/offline/` found no `digest`/`crypto.subtle`/hash-import over Quran bytes.
- **OPFS promotion is crash-safe and the staged content validator is the real gate.** `writeOpfsFile` (`opfs-cache.ts:225-240`) closes the stream in a `finally` before the temp is read back (`:372`) and validated (`:374`); `assertStagedQuranBytes` (`quran.worker.ts:154-166`) opens bytes via `sqlite3_deserialize` with `SQLITE_DESERIALIZE_READONLY` and checks count === 6236, coordinates, a text probe, and surah/ayah range + `globalIndex` contiguity — all strictly before `writePointer` (`:391`), the sole promotion gate. A partially-written DB can never become active.
- **`StagedValidationRejection` is re-thrown** (`opfs-cache.ts:50-61`, re-thrown at `:322`) so a content rejection NEVER silently falls back to IDB; only OPFS-mechanical failures fall through, and the IDB path re-runs `runStagedValidator` (`:423`) before put.
- **Fetch handler is structurally correct.** `event.respondWith` is invoked synchronously in every branch before any await (`service-worker.ts:409-453`); every runtime `cache.put` is guarded by `res.ok && isCacheable` and clones before storing (`:461/:482/:527/:569/:690`); `Response.error()`, opaque (status 0 → `ok` false), and consumed-body responses are never stored; no double-clone waste. **Exception:** `precache` (`:284`, `:293`) checks `res.ok` only — no `isCacheable`. Harmless today (all four precache targets are prerendered/static, so `hooks.server.ts` never runs on them), but latent: `applyHeaders` (`:87`) stamps `private, no-store` on *any* cookie-bearing response, and the SW's `fetch(url, {cache:"no-cache"})` sends cookies by default (`credentials: "same-origin"`). If `/` or `/en/app` ever becomes SSR, install would cache a personalized no-store shell into `APP_CACHE` — the one bucket `purgeUserCachesHandler` never clears.
- **Precache is atomic** (`service-worker.ts:274-298`): on ANY failure the catch runs `await caches.delete(APP_CACHE)` then `throw err`, so install fails with no half-cache; `activate` (`:304-316`) awaits `sw.clients.claim()` BEFORE any fetch is served.
- **`computeEvictions` math is correct.** Break condition `remaining <= CAP_COUNT && totalBytes <= CAP_BYTES && r.used >= cutoff` verified against 15-artifact/200MiB and 13-artifact/100MiB examples and 13 test cases; pinned exclusion filters `!pinned.has(id)` BEFORE ranking (`PINNED_ARABIC = [TanzilUthmani]`); TTL direction correct (`used == cutoff` KEPT).
- **Purge isolation verified end-to-end.** `purgeUserCachesHandler` (`:180-191`) deletes ONLY `PAGES_CACHE`/`DATA_CACHE`/data-meta; `APP_CACHE`, OPFS Quran DBs, and `eq-pack-*` are never referenced; ACK is posted on the transferred `MessagePort` only after the deletes complete, with try/catch so a missing port never throws.
- **`moveOpfsFile` feature-detects `FileSystemFileHandle.move()`** (`opfs-cache.ts:242-258`) and falls back to getFile → `writeOpfsFile(toName)` → `removeEntry(fromName)`; the fallback's non-atomicity is recovered by the legacy-adoption path (`:348-365`) which re-runs `verifyBytes` + `stagedValidator` before any pointer on next boot.

## Defects

### Medium

**M1. IDB put failure silently misreported as a successful cache** — `web/src/lib/workers/opfs-cache.ts:424`
*Evidence.* `createIdbStore.put` (`storage.ts:58-66`) wraps `idbPut` in `try { ... return true; } catch { return false; }`. `ensureIdbArtifact` calls `await store.put(spec.id, spec.id, bytes)` at `:424` with **no left-hand side** — the boolean is discarded — then unconditionally returns `{ bytes, store: "idb", downloaded: true }` at `:426`. The OPFS path throws on every write/verify failure (`:377/:387/:395/:397`); the IDB path does not. Per MDN a readwrite IDB tx hitting `QuotaExceededError` aborts atomically, so `idbPut` genuinely fails to store.
*Failure scenario.* Origin under storage pressure → `QuotaExceededError` on the put → `put` resolves `false` (bytes never persisted) → caller treats artifact as cached. `listIdbArtifacts`/`listCachedArtifacts` won't list it (nothing stored), so cache state diverges from the reported store; next session cache-misses and re-downloads. `stampLastUsed` (`:425`) also writes a `lastUsed` record for an artifact that does not exist, which `runPrune` never pairs nor clears.
*Suggested fix.* Await the put boolean and, on `false`, throw (honest contract) or return `store:"session"`/`downloaded:true`. Never return `store:"idb"` when the put failed.
*MDN.* https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/error

**M2. `listOpfsArtifacts` deletes in-flight download temps (race with `ensureOpfsArtifact`)** — `web/src/lib/workers/opfs-cache.ts:447-448`
*Evidence.* `filterSourceFiles` (`:133-135`) classifies EVERY `.sqlite.tmp` as `abandonedTemps` with no age/ownership check; `listOpfsArtifacts` removes them fire-and-forget: `void Promise.all(abandonedTemps.map((f) => removeOpfsFile(f.tag, f.name))).catch(() => {})` (`:447-448`). `ensureOpfsArtifact` writes its temp at `:371`, reads it back at `:372`, throws at `:373` if missing, validates at `:374`, and only renames at `:390` (`moveOpfsFile` opens the temp with `dir.getFileHandle(fromName)` at `:246`, which throws `NotFoundError` once removed). The temp must survive multiple real async I/O awaits. The worker allows interleaving (`ctx.onmessage` is fire-and-forget, `quran.worker.ts:507-509`); `pruneTranslations` is reachable mid-download via `:328`/`:487`; `pruneInFlight` (`opfs-retention.ts:73-81`) dedupes only prune-vs-prune; `pendingTranslationRunners` dedupes only same-sourceId.
*Failure scenario.* User opens translation X (`ensureArtifact(X)` suspended at `writeOpfsFile('X.sqlite.tmp')`); a second message completes translation Y and fires `void pruneTranslations(...)` → `listCachedArtifacts` → `listOpfsArtifacts` → removes `X.sqlite.tmp` → `ensureArtifact(X)` resumes and throws "staged temp unreadable" (`:373`) or `NotFoundError` inside `moveOpfsFile`. Download fails and must be retried. Active file and pointer are never touched — no corruption, no stale serve — but intermittent, user-visible download failure under multi-translation navigation. Self-healing on next access.
*Second, narrower trigger.* `deleteCachedArtifact` (`:491-495`) removes `tempFileName(id)` as well as `activeFileName(id)`, so `runPrune` evicting X while X is being **re**staged deletes X's temp directly, bypassing the `listOpfsArtifacts` sweep. Reachability is narrow — `filterSourceFiles` only nominates ids that already have a pointer + matching active file, and `ensureOpfsArtifact:339-347` returns early in that state unless `verifyBytes` throws (on-disk size ≠ catalogue `sizeBytes`) — but it matters for fix selection.
*Suggested fix.* **Serialize `listCachedArtifacts`/prune against the download queue.** The alternatives (track a `Set<sourceId>` of in-flight staging writes and skip those temps in `filterSourceFiles`; or only sweep temps older than a sentinel) fix the `:447-448` sweep but leave `deleteCachedArtifact:494` unguarded. See also L11 — the standalone sweeper that *should* own this cleanup is never called.
*MDN.* https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system

### Low

**L1. Byte budget under-counts precompressed prerendered `__data.json`** — `web/src/service-worker.ts:114` *(CONFIRMED — refuted in pass 2, reinstated and sharpened in pass 3; see re-verification)*
*Evidence.* `responseSize` (`:114-121`): `const cl = res.headers.get('content-length'); if (cl) { ... return n; } return 0;`. `recordDataEntry` (`:155-159`) propagates `sizeBytes = responseSize(res)`; `enforceDataBoundsInner` (`:210-220`) computes `totalBytes` from `sizeBytes` and breaks on `count <= DATA_MAX && totalBytes <= DATA_BUDGET_BYTES`. Grep found NO body-measurement fallback anywhere in the file. **The entries reaching this code are prerendered, not SSR** — verified in `build/`: the adapter-node middleware chain is `[..., serve_prerendered(), ssr]`, and `serve_prerendered` returns without calling `next()` for any path in the `prerendered` set (6539 entries, **2609** ending in `__data.json`; `/en/app/al-kahf/__data.json`, `/en/app/page/1/__data.json`, `/en/app/juz/1/__data.json` all present; 1298 under `/en/app` alone). Those are served by `sirv(path, {etag, gzip, brotli, setHeaders: undefined})` — `setHeaders` is passed only for the client dir — so they carry **no `cache-control` at all**: SvelteKit's `private, no-store` (`data/index.js:149/:173`) and `hooks.server.ts` `applyHeaders` are both bypassed, and `isCacheable` (`:56-61`) returns `true` on a null `cc`.
*Failure scenario.* sirv serves precompressed variants (6539 `.br` files in `build/prerendered`, including `__data.json.br` for reader routes) with `Content-Length` = **compressed** size while the Cache stores the **decompressed** body. Measured on `build/prerendered/en/app`: raw total 6.62 MiB vs br total 1.96 MiB (~3.4×); e.g. `/en/app/__data.json` raw 68885 / br 6986. Both possible browser behaviors break the budget, so the defect does not depend on resolving which holds: if `content-length` survives decoding, `totalBytes` under-counts ~3.4× and the 32 MiB cap admits ~110 MiB of real data; if the browser strips it on a decoded response, `responseSize` returns 0, `totalBytes` stays 0 regardless of entry count, and eviction falls back to count alone (`DATA_MAX=400`). Test blind spot: `responseWith()` (`service-worker-data-cache.test.ts:115-120`) hard-codes an accurate `content-length`, so the byte-cap test proves neither path.
*Suggested fix.* Measure at put time rather than trusting the header: `sizeBytes = (await res.clone().arrayBuffer()).byteLength`. A `Number(cl) || …` fallback is NOT sufficient — it still trusts a present-but-compressed `Content-Length`.
*MDN.* https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Length — not guaranteed (chunked TE, optional under HTTP/2), and reflects the encoded body; https://developer.mozilla.org/en-US/docs/Web/API/Cache

**L2. `touchRecency` read-modify-write is unserialized — LRU corruption** — `web/src/service-worker.ts:583` *(CONFIRMED)*
*Evidence.* `touchRecency` (`:583-588`): `const recency = (await metaGet('recency')) || {}; recency[key] = Date.now(); await metaSet('recency', recency);` — two yield points, no lock. `idb.ts:40-69` opens a SEPARATE transaction per op; no transaction spans the read-modify-write; two readwrite puts are serialized by IDB but both based on the stale snapshot — last writer wins. `serializeDataMeta` (`:123-128`) exists for the data-meta path and is absent for recency — confirming oversight. `handleNavigation` calls `touchRecency` from three branches (`:485/:493/:503`); `trimPages` (`:711-716`) scores by `recency[key] ?? 0` and evicts `scored.slice(0, reqs.length - PAGES_MAX)`.
*Failure scenario.* Rapid successive (or multi-tab) navigations A then B: both read `{k1:t1}`, A writes `{k1:t1,kA:tA}`, B writes `{k1:t1,kB:tB}` — `kA` lost. `trimPages` scores the just-visited page A as `0`, sorts it oldest, evicts it first. Self-healing (next visit re-adds recency); impact is cache-efficiency only, not data integrity.
*Suggested fix.* Route `touchRecency` through a `serializeRecency` lock analogous to `serializeDataMeta`, or store per-key recency records.
*MDN.* https://developer.mozilla.org/en-US/docs/Web/API/FetchEvent — SW single-threaded but async, fetch events interleave at awaits; https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API

**L3. Three page-cache deletion paths leave orphan entries in the recency map** — `web/src/service-worker.ts:182`
*Evidence.* `purgeUserCachesHandler` (`:182`) `await caches.delete(PAGES_CACHE)` — no `metaSet('recency', {})`. `purgeLegacyReaderPaths` (`:327-331`) meta cleanup (`:333-336`) only scans `DATA_META_PREFIX`. `handleNavigation` stale purge (`:501`) `await pages.delete(req).catch(()=>{})` — no recency cleanup. Only `trimPages` (`:717-723`) cleans recency.
*Failure scenario.* Over a long session the single `recency` record accumulates hundreds of keys for pages no longer cached. Not a bound violation (`trimPages` iterates `cache.keys()` and ignores orphan recency keys), but each `touchRecency` read-modify-write (deserialize → mutate → serialize the whole object) gets progressively slower and IDB bloats. Asymmetry with `purgeAllDataMeta` indicates oversight.
*Suggested fix.* After `caches.delete(PAGES_CACHE)`, also `await metaSet('recency', {})`; in `purgeLegacyReaderPaths`, filter/rewrite recency for deleted page keys alongside data-meta cleanup.

**L4. Exact-root `/quran` and `/_quran` are not in the bypass list** — `web/src/service-worker.ts:414-415`
*Evidence.* `:414` `if (url.pathname.startsWith("/quran/")) return;` and `:415` `if (url.pathname.startsWith("/_quran/")) return;` — a pathname of exactly `/quran` or `/_quran` matches neither, bypasses none of `:414-428`, and hits `:450-452` `event.respondWith(swrApp(req))`, whose `swrApp` (`:564-581`) puts into `APP_CACHE` on `res.ok && isCacheable`.
*Failure scenario.* Design intent (`docs/quran-system.md:32,95`) marks both roots BYPASS. A GET to the exact root that returns 200 would be stored in `eq-app-${version}`, mixing API/gateway bytes with the app shell. Zero impact today (the app always fetches subpaths per `lib/quran/environment.ts:8-9`; bare `/_quran` reaches the rest-param route with `artifact === ""` and is rejected by the `ALLOWED_ARTIFACTS` allowlist — `src/routes/_quran/[...artifact]/+server.ts:27` — while bare `/quran` has no same-origin route and no proxy in `hooks.server.ts`, so both 404 and `res.ok` is false) — but one new root route away from silently caching Quran-delivery bytes.
*Suggested fix.* `if (url.pathname === "/quran" || url.pathname.startsWith("/quran/")) return;` and likewise for `/_quran`, or anchor with `/^\/quran(\/|$)/`.

**L5. Pack fallback `ignoreSearch:true` can collide query-distinct `__data.json` keys** — `web/src/service-worker.ts:556`
*Evidence.* `:554-557` `const packHit = await caches.match(new Request(key), { cacheName: packName, ignoreSearch: true });` where `key = normalizeDataKey(req.url)`; `normalizeDataKey` (`:40-50`) retains every query param except `x-sveltekit-*` and `mode`. Pack entries are populated path-style via `offline-store.svelte.ts:228-231`.
*Failure scenario.* Offline + active pack, a request to a route whose `__data.json` varies by a retained query param (e.g. `/app/search/__data.json?q=foo` vs `?q=bar`) collapses onto the single pathname-only pack entry, serving the wrong body. Reader/juz/surah routes are path-keyed so unaffected; needs a query-varied route in the pack, last-resort only. (cache-isolation independently reviewed this path and judged it SAFE today because `gen-offline-pack.ts:34-39` produces path-only keys with no query variants — residual risk is a future query-varied route entering the manifest.)
*Suggested fix.* Constrain the fallback to path-only keys, or drop `ignoreSearch` and store pack entries under the same normalized key the live handler uses.
*MDN.* https://developer.mozilla.org/en-US/docs/Web/API/Cache/match

**L6. Controlled-but-unreloaded tabs never ACK the new version, stalling `pruneOldAppCaches` (cache leak)** — `web/src/service-worker.ts:397`
*Evidence.* `maybeFinalizeHandoff` (`:387-400`): `const allAcked = live.every((c) => acks[c.id] === version); if (!allAcked) return; await pruneOldAppCaches();`. `web/src/routes/+layout.svelte:49-57`: `const hadControllerAtBoot = Boolean(navigator.serviceWorker?.controller); const onControllerChange = () => { if (!hadControllerAtBoot) postAppReady(); };` — a tab that booted under the OLD SW does NOT call `postAppReady()` on takeover. The OLD SW already recorded `ack:${id} = oldVersion` (`onAppReady`, `:379-382`), so the new SW reads a stale ack.
*Failure scenario.* Two tabs on v1; user updates in tab A; v2 activates, `clients.claim()` takes over both, `UPDATE_TAKEOVER` broadcast. Tab A reloads → `ack:A = v2`. Tab B's reload guard was armed by `PREPARE_RELOAD` over BroadcastChannel — if that message was dropped (tab B had not run `update.hydrate()` when broadcast; BroadcastChannel does not buffer for late constructors), tab B never reloads, stays live under v2 with `ack:B = v1`. `allAcked` false → `pruneOldAppCaches` never runs → `eq-app-v1` retained until tab B closes. Safe (never premature deletion), but a cache-size leak.
*Suggested fix.* Drop the `!hadControllerAtBoot` gate and always `postMessage(APP_READY)` on `controllerchange`; or have the SW clear stale acks (value !== version) before the `allAcked` check.
*MDN.* https://developer.mozilla.org/en-US/docs/Web/API/Clients/claim ; https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerContainer/controllerchange

**L7. `hasTranslation` reports stale "cached" for evicted translations** — `web/src/lib/workers/quran.worker.ts:328`
*Evidence.* `:328` and `:487` both fire-and-forget `pruneTranslations` WITHOUT calling `refreshCachedTranslationIds()`. `refreshCachedTranslationIds` (`:347-353`) runs only once at boot (`:226`). `cachedTranslationIds` (`:76`) is only added to (`:351/:359`) or cleared on boot (`:350`); no path removes an id on eviction. `hasTranslationCached` (`:344`) = `translationDbs.has(sourceId) || cachedTranslationIds.has(sourceId)`. `runPrune` (`opfs-retention.ts:130-134`) deletes bytes/pointer/lastUsed but cannot touch the in-memory Set (different module, no callback hook).
*Failure scenario.* 13+ translations downloaded, exceeding `CAP_COUNT=12`; a new download triggers `pruneTranslations` → evicts oldest (say `en.sahih`) → UI queries `hasTranslation` for `en.sahih` → returns `true` (stale) → shows cached → on open, `fetchTranslationRunner` finds pointer gone and transparently re-downloads. Misleading cache-status UI + surprise re-download; self-heals only on worker restart.
*Suggested fix.* After `runPrune` returns a non-empty evicted list, `cachedTranslationIds.delete(id)` for each (and close/drop from `translationDbs`); or simply `await refreshCachedTranslationIds()` after prune.

**L8. OPFS→IDB fallback re-downloads bytes already fetched** — `web/src/lib/workers/opfs-cache.ts:327`
*Evidence.* `ensureOpfsArtifact` `:370` `const bytes = await downloadBytes(...)` then `:371` `writeOpfsFile(temp)`; on throw, `:375` removes temp and rethrows. `ensureArtifact` `:321-324` catches non-`StagedValidationRejection` and falls through to `return ensureIdbArtifact(...)` (`:327`), whose body re-runs `const bytes = await downloadBytes(...)` at `:422`. *MDN.* https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system — OPFS shares origin quota with IDB, so OPFS quota failure typically predicts an IDB constraint too.

**L9. `createOpfsStore.put` leaks `FileSystemWritableFileStream` when `write()` throws (dead code, but exported)** — `web/src/lib/workers/storage.ts:38`

**L10. `idbGet` omits `tx.onabort`/`tx.onerror` and can hang on a transaction-level abort** — `web/src/lib/workers/idb.ts:45` *(REFUTED in pass 2 — retained for the record; the abort fires `error` at pending requests, so `idbGet` rejects rather than hangs. The real residue is L12.)*

**L11. `sweepAbandonedTemps` is dead code, so temp cleanup only ever runs on the racy path** — `web/src/lib/workers/opfs-cache.ts:297`
*Evidence.* `sweepAbandonedTemps` (`:297-302`) is exported and deletes every `.sqlite.tmp` in the OPFS tree. Grep across the repo (excluding `node_modules`/`.svelte-kit`) finds exactly three references: the definition, and `opfs-cache.test.ts:21`/`:710`. **Zero production callers.** The only temp cleanup that actually runs in production is the fire-and-forget sweep inside `listOpfsArtifacts` (`:447-448`) — i.e. exclusively on the prune path that M2 shows is racy.
*Failure scenario.* No direct failure; this is the structural cause of M2's blast radius. A sweeper invoked once at worker boot — before any `ensureArtifact` can be in flight — is safe by construction, which the inline sweep is not.
*Suggested fix.* Call `sweepAbandonedTemps()` once during worker boot (alongside `refreshCachedTranslationIds`, `quran.worker.ts:226`) and delete the inline sweep at `:447-448`, leaving `listOpfsArtifacts` a pure read. This is the cleanest M2 fix and subsumes both of M2's triggers.

**L12. Dead IDB connections and `dbAvailable` are permanent latches with no recovery path** — `web/src/lib/workers/idb.ts:4`, `web/src/service-worker.ts:63`
*Evidence.* `openIdb` memoizes `Promise<IDBDatabase>` in `idbConnections` keyed `${dbName} ${storeName}` (`idb.ts:4-22`) and never evicts. Grep for `onclose`/`onversionchange`/`"close"` across `idb.ts`, `storage.ts`, `service-worker.ts` → zero hits. Separately, `dbAvailable` (`service-worker.ts:63`) is set `false` in the `metaSet`/`metaDel` catches (`:82`, `:91`) and is **never reset to `true`**; `db()` (`:65-68`) rejects unconditionally once latched.
*Failure scenario.* On a forced close (origin data evicted under storage pressure, or the user clears site data while the worker lives) every later `db.transaction()` on the cached handle throws `InvalidStateError`. That **rejects rather than hangs** — which is why L10 is correctly refuted — but the cache entry is never dropped, so a fresh `indexedDB.open()` that would succeed is never attempted, and pointer reads degrade to "no pointer" (re-download) for the life of the worker. In the SW the latch is coarser still: one transient `metaSet` failure disables recency + data-meta for the SW's whole lifetime, so `trimPages` scores every page `0` and `enforceDataBounds` loses its metadata. Both self-heal only on worker/SW restart.
*Suggested fix.* Wire `db.onclose` / `db.onversionchange` to delete the `idbConnections` entry so the next call reopens; make `dbAvailable` a re-probe (e.g. clear the latch on a later successful `metaGet`, or drop it and rely on the existing per-call try/catch) instead of a one-way switch.
*MDN.* https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/close_event

**I1. Hardcoded `IDB_VERSION=1` + `storeName` parameter is a version-evolution trap** — `web/src/lib/workers/idb.ts:2`
*Evidence.* `idb.ts:2` `export const IDB_VERSION = 1;`; `:12-16` `onupgradeneeded` creates the store only if missing. The version is a module constant, not derived from the stores requested. Safe today: every dbName maps to exactly one storeName (`(easyquran-quran, artifacts)`, `(easyquran-pointers, opfsPointers)`, `(easyquran-meta, lastUsed)`, `(easyquran-sw-meta, meta)` — `idb.test.ts:208-223`).
*Failure scenario.* A future change adds a second store to an existing db (e.g. `metadata` alongside `artifacts` in `easyquran-quran`): `openIdb("easyquran-quran", "metadata")` at v1 finds the db already at v1, `onupgradeneeded` does not fire, the store is never created, first tx throws `NotFoundError`.
*Suggested fix.* Pin one-store-per-db as a documented invariant (drop `storeName`), or compute `IDB_VERSION` from a per-db store registry so a new store forces a bump.
*MDN.* https://developer.mozilla.org/en-US/docs/Web/API/IDBOpenDBRequest/upgradeneeded_event

## Refuted (checked, dropped)

- **Navigation returns HTTP 5xx to the user instead of falling back to cached page** (`cache-routing`, `web/src/service-worker.ts:488`). The two-branch logic is spec-correct NetworkFirst: `fetch` RESOLVED (any HTTP status incl. 5xx) → server reachable → return authoritative response (`:488`); `fetch` REJECTED → `network = null` (`:477`) → genuine network failure → offline cache ladder (`:490-509`). The ladder is an OFFLINE fallback, not an HTTP-error fallback. The suggested fix (`if (network && network.ok) return network;`) would serve stale cached pages on 404/401/403/429, which is worse. No project document describes an HTTP-error fallback ladder; the only "Reader fallback ladder" (`docs/quran-system.md:106`) describes Worker data fetching, a different subsystem.

A second pass re-checked all 13 findings against current (2026) primary sources — MDN (prose + Browser-compatibility/Specifications tables), Can I Use, the WHATWG/W3C specs, and browser release notes / bug trackers — with an independent adversarial reviewer per finding. **Net: the audit holds and is sharpened.** Both mediums (M1, M2) and the eight previously-UNCERTAIN low/info findings (L2–L9, I1) are re-confirmed — their load-bearing platform premises all verify against primary sources. Pass 2 refuted two findings (L1, L10); **pass 3 overturned the L1 refutation** (below) and let L10's stand, so **one finding is refuted (L10)** and two new ones were added (L11, L12). All stage-1↔stage-2 cross-checks agreed; L10's skeptic pass hit a provider rate-limit (429) and was adjudicated manually against the spec (noted at L10).

> Process note on L1, superseded twice. Pass 2's refutation first cited `sveltejs/kit#7778`, a GitHub issue whose page contains no resolution and does **not** support the claim; re-checking by hand against the **installed** SvelteKit source appeared to rescue the conclusion. Pass 3 shows the conclusion itself was wrong: the installed-source evidence was real but scoped to the SSR data path, which prerendered routes never enter. **Lesson recorded (revised): confirming the cited code exists is not the same as confirming it executes on the path in question — trace the request, not just the source.**

- **M1. IDB quota failure silently misreports cache state** — FINAL **medium (CONFIRMED)**. A readwrite IDB tx hitting `QuotaExceededError` aborts atomically and the put does not persist (W3C IndexedDB; real-world localForage #359); `ensureIdbArtifact` discards `createIdbStore.put`'s `false`, stamps a phantom `lastUsed`, and reports the artifact cached — a silent per-session re-download loop, self-healing, no corruption. `https://w3c.github.io/IndexedDB/`
- **M2. listOpfsArtifacts deletes in-flight download temps** — FINAL **medium (CONFIRMED)**. OPFS `removeEntry`/`getFileHandle` acquire no lock (WHATWG File System Standard §2.4); a cross-translation prune can delete a staged temp mid-validation and break the move. Real race in the designed-for multi-translation workload, self-healing. `https://fs.spec.whatwg.org/`
- **L2. touchRecency read-modify-write unserialized** — FINAL **low (CONFIRMED)**. One SW instance serves all tabs and IDB readonly-txs overlap (W3C service-workers); the unlocked `metaGet→mutate→metaSet` lets two navigations clobber the recency record so `trimPages` may evict a recently-used page. `https://www.w3.org/TR/service-workers/`
- **L3. Page-cache deletions orphan recency keys** — FINAL **low (CONFIRMED, was UNCERTAIN)**. Three deletion paths never reconcile the single `recency` IDB record; orphans grow a record that is whole-object serialized each touch. Eviction correctness is unaffected (orphans are invisible to `trimPages`' `cache.keys()` scoring). `https://www.w3.org/TR/IndexedDB/`
- **L4. Exact-root `/quran`, `/_quran` not in the bypass list** — FINAL **low (CONFIRMED, was UNCERTAIN)**. `'/quran'.startsWith('/quran/')` is `false` (ECMA-262); latent fail-open with **zero** impact today (origin-gated + router-level catch-all 404). `https://tc39.es/ecma262/#sec-string.prototype.startswith`
- **L5. Pack fallback `ignoreSearch:true` collision** — FINAL **low (CONFIRMED, was UNCERTAIN)**. `ignoreSearch` strips the whole query all-or-nothing (MDN; W3C ServiceWorker #1798); dormant because pack keys are path-only and the reader's only query param (`mode`) is pre-stripped. `https://developer.mozilla.org/en-US/docs/Web/API/Cache/match`
- **L6. Stale ACK stalls `pruneOldAppCaches`** — FINAL **low (CONFIRMED, was UNCERTAIN)**. `clients.claim()` takes over old-booted tabs without reload and fires `controllerchange` (MDN); the `!hadControllerAtBoot` guard skips re-ACK, which can stall `pruneOldAppCaches` — safe-direction (no premature delete), self-heals on tab close/unfreeze. `https://developer.mozilla.org/en-US/docs/Web/API/Clients/claim`
- **L7. hasTranslation stale after eviction** — FINAL **low (CONFIRMED, was UNCERTAIN)**. `cachedTranslationIds` is add-only; pruned ids keep reporting cached (skipped prefetch + internal `servedBy:'local'` telemetry mislabel); self-heals on worker restart. `https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers`
- **L8. OPFS→IDB fallback re-downloads bytes** — FINAL **low (CONFIRMED, was UNCERTAIN)**. Failed OPFS bytes are function-local; the IDB path re-fetches, often futilely under the shared per-origin quota (MDN Storage quotas and eviction). `https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria`
- **L9. createOpfsStore.put leaks WritableFileStream** — FINAL **low (CONFIRMED, was UNCERTAIN)**. No try/finally; a `write()` throw leaks the stream + its lock (`close()` is the only commit, WHATWG fs §2.5). Dead code (zero production callers) today. `https://fs.spec.whatwg.org/`
- **I1. `IDB_VERSION=1` + `storeName` parameter trap** — FINAL **info (CONFIRMED, was UNCERTAIN)**. A second store added to an existing db at v1 never fires `onupgradeneeded`, so `db.transaction(newStore)` throws `NotFoundError`; one-store-per-db holds today. `https://www.w3.org/TR/IndexedDB-3/`
- **L1. Byte budget under-counts precompressed prerendered `__data.json`** — FINAL **low (CONFIRMED)**, after pass 2 refuted it and **pass 3 overturned that refutation**. Pass 2 argued `__data.json` is never SW-cached because SvelteKit 2.70.1 stamps `cache-control: private, no-store` on it (`node_modules/@sveltejs/kit/src/runtime/server/data/index.js:149` and `:173`, verified in the installed tree). That header is real but **only on the SSR data path**. Verified in `build/`: adapter-node's middleware chain is `[..., serve_prerendered(), ssr]`, and `serve_prerendered` returns without `next()` for any path in the `prerendered` set — 6539 entries, **2609** of them `__data.json`, including `/en/app/al-kahf/__data.json`, `/en/app/page/1/__data.json`, `/en/app/juz/1/__data.json` (1298 under `/en/app` alone). Those never reach `data/index.js` *or* `hooks.server.ts`; they are served by `sirv(path, {etag, gzip, brotli, setHeaders: undefined})` with **no `cache-control` header**, so `isCacheable` returns `true` and they populate `eq-data-v1`. The budget gap is not only reachable but systematic: sirv serves `.br` variants whose `Content-Length` is the compressed size while the Cache stores the decompressed body (en/app: 6.62 MiB raw vs 1.96 MiB br, ~3.4×). Governing evidence is the built adapter output, not the Kit source. See L1 above for the full chain and the corrected fix.
- **L10. `idbGet` omits `tx.onabort`, can hang on abort** — FINAL **info (REFUTED, was low/UNCERTAIN)**. IndexedDB 3.0 §5.5 (abort-transaction) step 6.4 fires an `error` event at every request still pending in the transaction's request list on abort — corroborated by MDN, javascript.info, and SO. Since `idbGet` wires `req.onerror`, the promise rejects with `AbortError`; it does **not** hang. The skeptic pass was lost to a 429, so this was re-adjudicated by hand against the spec + an independent web search (both agree). `https://w3c.github.io/IndexedDB/#abort-transaction`

### Larger fact (corrected in pass 3): `eq-data-v1` is split by serving path

Pass 2 concluded the whole `eq-data-v1` SWR + data-meta subsystem was inert in production. **That is wrong.** The subsystem is live, and which `__data.json` reaches it is decided by whether the route is prerendered:

- **Prerendered (2609 files, all Arabic reader routes + marketing):** served by sirv ahead of `ssr`, no `cache-control` at all → `isCacheable` true → **cached in `eq-data-v1`**. These are the same files `gen-offline-pack.ts` scans out of `build/prerendered`, so the SW data cache and the offline pack are fed from one source — consistent by construction, and `docs/quran-system.md:93`'s description of `eq-data-v1` as a live bounded cache is accurate.
- **SSR (`prerender = false` — the `/t/**` translated reader routes):** SvelteKit stamps `private, no-store`, `applyHeaders` preserves it via the `hasNoStore` branch, `isCacheable` rejects → **never cached**. Translated reader data is network-only in the SW and relies on the SSR disk-TTL cache instead.

The practical consequence is a bound that does not hold: the 32 MiB `DATA_BUDGET_BYTES` is enforced against compressed `Content-Length` values (or zeros), so the real ceiling is several times higher — see L1. **Suggested team follow-up:** fix the measurement per L1, then decide whether 32 MiB is still the intended number now that it will actually bind.
