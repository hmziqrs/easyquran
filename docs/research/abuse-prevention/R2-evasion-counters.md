# R2 — Fingerprint Evasion and the Countermeasures That Actually Work

**Scope.** How a determined abuser defeats a multi-signal device fingerprint built from three sources — server-side network/ASN, client-side JavaScript, and credential-linked state — and which countermeasures survive that abuse. Written as adversarial input to a threat model for a self-hosted Quran reader (Arabic + translated, public content, small team, no anti-fraud vendor).

**Date.** October 2026. All sources published 2024–2026 unless marked otherwise.

**Method / confidence note.** Search-engine HTML endpoints (DuckDuckGo, Mojeek, Startpage) were captcha-blocked or Anubis-walled during collection; Brave Search worked intermittently before rate-limiting; Bing returned a broken index. Where a search engine was unavailable I fell back to open APIs (OpenAlex, arXiv Atom, Semantic Scholar, HN Algolia, GitHub) and to direct fetches of primary sources. Every URL in §Sources was fetched successfully or returned inside a search result set — except three, flagged inline as `[pointer, unverified]`. Vendor blogs (Castle, DataDome, Cloudflare, Fingerprint, Spur, Rebrowser) are interested parties; their _technique descriptions_ are corroborated by independent academic work (FP-Inconsistent, FP-Agent, Brotector) and by attacker-side source code, which is why they are cited. Treat vendor _accuracy claims_ as marketing unless an independent measurement is cited alongside.

## 0. The threat model this report assumes

Three adversary tiers, because countermeasures that stop tier 1 are free and countermeasures that stop tier 3 are not:

| Tier                                | Capability                                                                                                                                           | Realistic motivation against a Quran app                                                                                                             |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **T1 — Script kid / off-the-shelf** | `puppeteer-extra-plugin-stealth`, `undetected-chromedriver`, a datacenter proxy, `navigator.webdriver` patched                                       | Full-text scrape, dump the DB, republish as an app, ad-farm the content                                                                              |
| **T2 — Funded scripter**            | Patched Chromium or Camoufox, residential/mobile proxy pool, per-account proxy pinning, `rebrowser-patches` or Patchright, headful on a real desktop | Mass account creation, review/rating manipulation, competitor impersonation in app stores                                                            |
| **T3 — Organised / state-adjacent** | Fresh VM or real device per identity, browser-as-a-service, human-in-the-loop for challenges, real payment instruments, patient (weeks)              | Coordinated influence over religious-content narratives; targeted harassment of a specific community; defacement attempts via user-submitted content |

The key structural point: **the fingerprint is not the target; the _link_ is.** An attacker who can present a fresh, internally consistent fingerprint per request has beaten client-side fingerprinting entirely. What they cannot cheaply hide is (a) that a _credential_ is reused, (b) that two identities share a _resource_ (payment instrument, device token, ASN bucket, timing template), or (c) that their timing is _inhuman in aggregate_ even when each individual request looks fine. Sections 1–4 are about the evasion; sections 5–7 are about the residue.

## 1. Identifier rotation

### 1.1 What each rotation primitive actually clears

| Primitive                                                                                                              | Clears                                                                                | Leaves intact                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cookies / localStorage / IndexedDB wipe                                                                                | Cookie ID, any localStorage-seeded fingerprint salt                                   | Canvas/WebGL/audio hash, fonts, screen, GPU, timezone, TLS/JA4, ASN                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Incognito / private window                                                                                             | Storage; _not_ network identity                                                       | Everything device-level. Incognito is detectable but the reliable detectors are narrow and browser-version-specific — `navigator.storage.estimate().quota < 120 MB` worked Chrome 74–84 only, IndexedDB-open-throws worked Firefox ~88 only, FileSystem write-timing worked Chrome ~76–89. Fingerprint vendors now sell incognito as a _risk signal_ via server-side inference, not a browser quirk ([fingerprint.com/blog/incognito-mode-detection](https://fingerprint.com/blog/incognito-mode-detection/)) |
| Fingerprint-spoofing extension (CanvasBlocker, Canvas Fingerprint Defender, Chameleon)                                 | Canvas pixel hash                                                                     | Its own presence. The extensions inject noise via `Math.floor(Math.random()*10)-5` on r/g/b and wrap `toDataURL` in a **Proxy** object. `toString()` does _not_ reveal a Proxy; error-stack strings do — `e.stack.indexOf('chrome-extension') > -1` and matching the extension's store ID in the stack produced clean detection ([blog.castle.io/detecting-noise-in-canvas-fingerprinting](https://blog.castle.io/detecting-noise-in-canvas-fingerprinting/))                                                 |
| Anti-detect browser (Undetectable, Hidemium, GoLogin, Multilogin, AdsPower, DICloak)                                   | Everything, _per profile_ — own cookies, own config, own proxy, own canvas/audio seed | Its own injection artefacts and deleted-API artefacts; on Chromium-claimed profiles, usually nothing in JS                                                                                                                                                                                                                                                                                                                                                                                                    |
| Patched Chromium / engine-level spoof                                                                                  | The JS-observable lie entirely                                                        | Statistical implausibility of the claimed device, TLS stack, and cross-signal consistency                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Fresh VM per request                                                                                                   | Everything                                                                            | Datacenter ASN unless egressed through residential; GPU-class clustering; near-zero browsing history; TLS/JA4 uniformity across "different" users; timing entropy                                                                                                                                                                                                                                                                                                                                             |
| Browser-as-a-Service (`Rebrowser` cloud browsers, `Scrappey` "Clearcote" patched Chromium, Camoufox `launch_server()`) | The engineering cost of all of the above                                              | That the _service_ is the common ancestor — all its customers share an operator's cadence and, in practice, a small number of fingerprint templates                                                                                                                                                                                                                                                                                                                                                           |

### 1.2 Where each one breaks against a three-layer fingerprint

**Engine-level spoofing is genuinely strong.** Camoufox rewrites fingerprint values in Firefox's C++ layer, not via JS injection, so `toString()` and property descriptors read native; it also runs Playwright's page agent in an isolated world (Juggler), sets `navigator.webdriver = false`, makes `set_input_files`/`fill` fire trusted events, and generates the identity from a real-device distribution with a coherence filter (`coherence.py` rejects combinations no real machine produces). It explicitly _does not_ noise canvas pixels on the host OS, on the stated grounds that "noise would only mark the browser as a spoofer" ([github.com/daijro/camoufox](https://github.com/daijro/camoufox)). This is the correct call and it defeats every naive canvas-noise detector.

**But Camoufox's own README hands you the detectors.** It ships two admissions that are directly actionable:

1. "Camoufox presents Firefox identities only. Some WAFs test SpiderMonkey engine behaviour, which no amount of spoofing turns into Chromium." → If your visitor claims Chrome, test V8-specific behaviour; because every engine-level spoofer must claim _some_ engine to be believed, cross-engine behaviour tests catch the mismatch rather than the lie.
2. Canvas readback "on another OS" returns random data "as `privacy.resistFingerprinting` does in LibreWolf" → the spoofer's canvas signature is _Tor/LibreWolf-shaped_, which is rarer than stock Firefox. A canvas population that clusters on a resistFingerprinting distribution is itself the anomaly.

**Anti-detect browsers leak in two specific places.** Castle's teardown of Undetectable found that for claimed non-Chromium profiles the tool injects a ~2,500-line obfuscated script (obfuscator.io), and that script's `toString` patching is _incomplete_: it patches `eval.toString` but not `toString.toString`, so `eval.toString.toString()` reveals injected code ([blog.castle.io/anti-detect-browser-analysis-how-to-detect-the-undetectable-browser](https://blog.castle.io/anti-detect-browser-analysis-how-to-detect-the-undetectable-browser/)). For claimed Chromium profiles the JS lies are skipped — but the injected script still installs a `MutationObserver` that calls `document.getElementsByTagName` on iframe insertion. Overriding `getElementsByTagName` and throwing inside it dumped a stack containing `ready` and `iframeCheck`, which is a high-accuracy sender-side signature.

Hidemium leaks _nothing_ in the way of modified getters, and instead leaks by **deletion**. It deletes `navigator.share`, `navigator.canShare`, `NetworkInformation.prototype.downlinkMax`, `BarcodeDetector`, `ReportBody`, `CSPViolationReportBody`, `PaymentInstruments` and more to match the claimed OS. On a genuine Chrome 134/macOS those APIs exist, so the detection is: _claim Chrome ≥88 on macOS and present none of `BarcodeDetector`/`ReportBody`/`CSPViolationReportBody`/`navigator.share`_ ([blog.castle.io/detecting-hidemium-fingerprinting-inconsistencies-in-anti-detect-browsers](https://blog.castle.io/detecting-hidemium-fingerprinting-inconsistencies-in-anti-detect-browsers/)). Castle themselves flag the fragility: it breaks the moment the vendor stops deleting those properties.

**The generalisable lesson** is the one Castle states and the academic work confirms: don't hunt fixed signatures, hunt _expectation violations_. Given a claimed `(browser, version, OS, GPU class)`, the set of APIs, WebGL parameters, codec answers, font presence and CSS media features is largely determined. Anything outside that envelope is a lie, regardless of which tool told it.

**Browser-as-a-Service inverts the economics but creates a chokepoint.** The Camoufox README's own sponsor list is a map of the ecosystem: Layer3 Intel advertises "70M+ residential, mobile & ISP proxy IPs tracked across 200+ providers" and a "<40ms API" specifically to tell you whether "the IPs your provider sells you are clean, or already known and flagged." When even the anti-detect tool's sponsors sell detection of the anti-detect stack, the stack is not a secret. The realistic posture is not "detect Browser-as-a-Service," it is "make each BaaS _instance_ pay a cost" — see §9.

### 1.3 Credential-linked signals are the ones rotation cannot touch

Rotation is cheap for _anonymous_ traffic and expensive for _authenticated_ traffic. The moment an attacker logs in with a credential — even a freshly registered one — they have created a durable object that the defender controls:

- Registration-time signals that must be _consistent_ for the account to be usable later (e.g. an account created from a German residential IP with an `en-GB` locale is not, by itself, actionable, but it is a permanent, queryable fact).
- Recovery channels (email domain, phone range) that are enumerable in bulk.
- The account's _own_ behavioural history, which becomes a baseline the attacker must now maintain.

Castle's 2026 release of an open-source disposable-phone-number list, built from "real abuse activity," and their earlier disposable-email list, exist precisely because these are the residues that survive rotation ([blog.castle.io/sms-verification-abuse-at-scale-releasing-our-open-source-disposable-phone-number-list](https://blog.castle.io/sms-verification-abuse-at-scale-releasing-our-open-source-disposable-phone-number-list/)). Against a small self-hosted app, the practical version is: **stop treating a fresh account as a fresh user.**

## 2. IP rotation

### 2.1 The pools

Residential proxies exit through real ISP subscriber addresses, sourced by five documented methods: SDKs bundled into free apps that pay per install, free VPNs with buried terms, compromised IoT (streaming sticks, digital picture frames, aftermarket infotainment), malware in pirated content, and paid bandwidth-sharing schemes ([FBI PSA I-031226-PSA, March 2026](https://www.fbi.gov/investigate/cyber/alerts/2026/evading-residential-proxy-networks-protecting-your-devices-from-becoming-a-tool-for-criminals)). Providers "claim to offer 30-100 million IPs" ([Cloudflare Bot Management ML v8](https://blog.cloudflare.com/residential-proxy-bot-detection-using-machine-learning/)). Mobile pools sit behind CGNAT, which is why they are the premium tier for account abuse: hundreds of subscribers share one public IP, so the address has a legitimate-looking reputation and blocking it is collective punishment.

Scale and legality, for calibration: the US DOJ dismantled Anyproxy/5socks in May 2025 — 7,000+ proxies for sale at $9.95–$110/month, running since 2004, >$46M revenue (~$3.8M/yr, i.e. _small_) ([justice.gov](https://www.justice.gov/usao-ndok/pr/botnet-dismantled-international-operation-russian-and-kazakhstani-administrators)). Google disrupted the IPIDEA residential proxy network. The market is real but not monolithic.

### 2.2 Why IP reputation fails, with numbers

- **Cloudflare measured that 4 out of 5 requests from residential-proxy IP addresses are legitimate direct household traffic.** Blocking on IP reputation on a residential address gets one decision right in five.
- **Node churn:** an exit node exists only while the hosting app is running. Close the app, the node vanishes; reopen it, it may return, or the provider backfills a different device in a different city.
- **Resale:** across major providers, "on average **44.1% of IPs** are shared — the same residential IP appears in more than one provider's pool" ([ipgeolocation.io, July 2026](https://ipgeolocation.io/blog/how-residential-proxy-detection-works/)). Blocking one provider's ranges leaks the same device through another.
- **ISP reassignment** turns yesterday's burnt exit node into today's clean subscriber. Any entry without a last-seen date is a false positive waiting to happen.
- **Geofeed laundering (RFC 8805):** a provider publishes a CSV declaring datacenter IPs to be in a residential city; MaxMind/Google/Cloudflare ingest it, and a Kansas rack is sold as "Premium New York Residential." Reported by a competing proxy vendor on Hacker News ([news.ycombinator.com item 47286086](https://news.ycombinator.com/item?id=47286086)) — self-interested, but the mechanism is verifiable from RFC 8805 itself.

### 2.3 What state makes rotation hard

Rotation beats per-IP thresholds. It does not beat these:

1. **Credential reuse.** N logins across N IPs is not N independent events; it is one credential exercising N times. Per-IP counters see nothing; per-credential counters see everything. This is the single highest-leverage countermeasure in this document.
2. **TLS/JA4 + HTTP/2 fingerprint uniformity.** A pool of residential exits still terminates a _client_ stack. Twenty "different users" presenting byte-identical JA4, identical header order, identical `Accept-Encoding`, and identical HTTP/2 SETTINGS frames are one operator. The counter-counter is real (curl-impersonate, got-scraping, per-profile channel pinning) and a proxy-industry practitioner states the tradeoff bluntly: datacenter proxy + properly impersonated TLS "had a ~91% success rate" vs residential proxy + default Python headers "around 60%" ([r/ProxyEngineering, May 2026](https://www.reddit.com/r/proxyengineering/)) `[pointer, thread title/summary seen in search results]`. Cloudflare's ML v8 also reports that residential proxy traffic is distinguishable by network latency (multiple hops) — but they abandoned latency alone because satellite-ISP users are false positives.
3. **Cadence and endpoint focus.** Cloudflare observed residential-proxy traffic concentrating on `/login`, `/auth/login`, `/api/login`. On a Quran reader the equivalent is: sequential surah/page enumeration from many IPs, all with identical inter-request delay distributions, all hitting no images/fonts/CSS, all with zero referrer chains. Content scraping has a _shape_ that is orthogonal to the IP.
4. **Session-to-IP stability mismatch.** Real users keep roughly stable exit ASNs (home ISP, mobile carrier) and shift slowly. A rotating gateway produces an ASN change per request _inside one browsing session_, or worse, an ASN change between the HTML request and the first XHR — observable purely server-side if you log `X-Forwarded-For` lineage per session ID.
5. **Tor.** Tor exit IPs are published and enumerable; Tor Browser additionally presents a deliberately uniform fingerprint, so the _population_ is near-anonymous but the _cohort_ is trivially identified. Tor is not a good tool for account abuse (captcha walls, exit-list blocking) and is mostly irrelevant to content scraping of public data, because the content is already public.

### 2.4 The residual-honest conclusion on IP

For a public Quran API, IP rotation is not an evasion, it is the _expected_ traffic shape — readers are global, mobile, and behind CGNAT. Build IP signals as **cost multipliers and correlation edges**, never as allow/deny. Blocking residential ranges on a Quran app would be an own-goal against exactly the audience the app exists for.

## 3. Spoofing detection: finding an _inconsistent_ fingerprint

This is the section with the best independent evidence base. The headline result:

> **FP-Inconsistent** (Venugopalan, Munir, Ahmed, Wang, King, Shafiq; arXiv 2406.07647, v1 Jun 2024, v3 Sep 2025, published at ACM IMC'25 as 10.1145/3730567.3732919). A honey site with DataDome and BotD was fed ~500,000 requests from **20 commercial bot services** selling "realistic and undetectable traffic." **Average evasion rate 52.93% against DataDome, 44.56% against BotD.** The authors then mined _space_ (two attributes in one fingerprint) and _time_ (one attribute at two points) inconsistency rules. Deploying those rules **reduced evasion by 48.11% (DataDome) and 44.95% (BotD)** — i.e. roughly halved the effective bypass rate, with no new vendor tooling.

That is the strongest available argument that consistency-checking, not vendor tools, is the correct first investment. Two corollaries:

- Roughly half of paid "undetectable" bot traffic passes best-in-class commercial anti-bot. If you were considering buying one of those vendors, that number is your expected value.
- The fix that worked was _not_ a better fingerprint. It was a change detector over the fingerprint the bot already sent.

### 3.1 The detector catalogue, by signal family

**UA vs Client Hints (highest yield, zero client JS).**
In unmodified Puppeteer headless the two disagree loudly and immediately: the UA string carries `HeadlessChrome/125.0.0.0` while `sec-ch-ua` says `"Chromium";v="125", "Not.A/Brand";v="24"` — note _`Chromium`_, not `Google Chrome` — and `navigator.userAgentData` is **empty** where a real Chrome populates `brands`/`mobile`/`platform`. Real Chrome also sends `sec-ch-ua-form-factors: "Desktop"`, which Puppeteer-Chromium omitted ([deviceandbrowserinfo.com — unmodified headless Chrome with Puppeteer, June 2024](https://deviceandbrowserinfo.com/learning_zone/articles/fingerprint-unmodified-chrome-puppeteer)). Once the attacker sets a UA string by hand, the failure mode inverts: now the _UA is fine but everything downstream of it is not_ — hints version, `userAgentData.getHighEntropyValues()` emptiness (Brotector's `UAOverride` test fires on exactly this), and the version-gated API set.

The general rule, from Castle: _validate that expected browser features are present for the claimed environment_, and treat the claim as a hypothesis to falsify. Their worked example is BarcodeDetector on Chrome ≥88/macOS.

**Engine/dialect mismatch.** If `navigator.userAgent` claims Chrome but SpiderMonkey-specific behaviour is observable (or vice versa), the engine is not the claimed engine. Camoufox concedes this class of test is unwinnable for them.

**WebGL / GPU.** Two distinct tests:

- _Software-renderer tell._ `SwiftShader`, `llvmpipe`, `ANGLE (… Microsoft Basic Render Driver)` and the generic `WebKit WebGL` pair are renderer strings that essentially only appear in VMs and CI. Compare against the claimed GPU class for that OS.
- _Spoof-detection._ Unmodified headless Puppeteer on macOS reported `webGLVendor: "Google Inc. (Intel)"` and renderer `"ANGLE (Intel, ANGLE Metal Renderer: Intel(R) Iris(TM) Plus Graphics, Unspecified Version)"` where the human machine reported `"Google Inc. (Intel Inc.)"` / `"ANGLE (Intel Inc., … OpenGL Engine, OpenGL 4.1)"` — same hardware, different string shape because it is not the same driver path. Conversely Undetectable, when faking Safari, declares `Unmasked Vendor: "Google Inc. (Apple)"` with `Unmasked Renderer: "ANGLE (Apple, ANGLE Metal Renderer: Apple M2, Unspecified Version)"` while simultaneously declaring `Vendor: "WebKit"` / `Renderer: "WebKit WebGL"` — an internal pair no Apple browser produces.

**Canvas.** Two independent techniques with different failure profiles:

1. _Known-pixel proof of work._ Fill a canvas with `rgba(0,127,255,1)`, read back via `getImageData`, assert every r/g/b/a is exact. Noise-injecting extensions and naive `toDataURL` overrides fail this immediately.
2. _Function-identity side effects._ `Object.setPrototypeOf(fn, fn)` throws `TypeError: Cyclic __proto__ value` for a native function and **does not throw** for a `Proxy` — a Proxy-transparent detection that `toString()` cannot do. And `getImageData` called with bad arguments produces an `Error.stack` containing `chrome-extension://<id>/...`, which identifies the specific extension by its store ID.

Camoufox's deliberate choice _not_ to noise canvas on the host OS means test (1) passes for Camoufox — and its noise-on-other-OS mode makes it look like LibreWolf/Tor Browser, which test (1) also passes but which is statistically rare.

**Audio, fonts, voices, codecs, media devices.** These are the "weak signals" that matter only in combination. Concrete inconsistency pairs from the same source:

- `Accept-Language` / `navigator.languages` / `navigator.language` / `speechSynthesis.getVoices()[0].lang` / `Intl.RelativeTimeFormat().resolvedOptions().locale` are five independent readings of one fact and should agree. "Someone whose accept-language is en-GB but whose default speechSynthesis voice is Russian" is the canonical case.
- Voice _count_ and _Google-voice presence_ separate real Chrome from Chromium: 176 voices / 19 Google voices (human Chrome) vs 157 / 0 (Puppeteer's Chromium).
- `screen.availHeight` differed 1440 (headless) vs 1415 (real) on the same machine — not absolute, but a direction.
- Media codecs differ by host OS install state — on Linux the answer depends on installed codec libraries.
- Camoufox co-generates fonts, voices, a GPU and media devices _seeded by one identity_ precisely because mismatches here are how it gets caught.

**Timezone / locale vs IP.** Camoufox's `geoip=True` sets timezone, locale, geolocation and WebRTC IP from the proxy's exit IP because these must agree. The inverse is the detector: timezone `Asia/Riyadh`, `Accept-Language: en-US`, IP in Frankfurt, and `Intl` resolving to `en-GB` is four-way incoherent.

**`navigator.webdriver` and CDP artefacts.** §4.

**Missing/extra APIs.** Two directions, both used:

- _Missing-but-should-exist:_ Hidemium's deleted properties (above); absent `userAgentData`; absent `sec-ch-ua-form-factors`; `BarcodeDetector` absent on Chrome ≥88/macOS.
- _Extra-but-shouldn't-exist:_ `window.InstallTrigger` and `window.mozRTCPeerConnection` bolted onto Chromium to fake Firefox; `window.safari` objects synthesised in a Chromium build; `delete window.WebGL2RenderingContext` to model a browser that lacks it.

### 3.2 The practical detector: a consistency lattice, not a checklist

Rank signals by _how hard a sender can keep them consistent_, not by how distinctive they are:

| Rank | Signal class                                                                                                        | Why hard for the sender                                                                                                        |
| ---- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1    | **Space consistency**: (UA, CH, `userAgentData`, version-gated API set, feature presence)                           | Requires a per-version browser knowledge base; every browser release invalidates it                                            |
| 2    | **Time consistency**: same attribute, two different points in one session                                           | Requires stateful lying; noise-injection and randomisation defeat themselves here                                              |
| 3    | **Engine dialect**: V8 vs SpiderMonkey vs JavaScriptCore behaviour under stress                                     | Requires porting a browser engine                                                                                              |
| 4    | **Locale/timezone/`Intl`/IP coherence**                                                                             | Requires geo-consistent proxy selection _and_ matching locale seeds                                                            |
| 5    | **Headless-vs-headful tells** (`webdriver`, `webdriver` switch, headless UA, pointer media, wheel tick granularity) | Trivially patched, but patches are detectable by rank-1/2 tests                                                                |
| 6    | **Renderer strings**                                                                                                | Requires spoofing consistently across `gl.getParameter`, `WEBGL_debug_renderer_info`, WebGPU adapter limits, and canvas pixels |
| 7    | **Canvas/audio hashes**                                                                                             | Cheap to spoof, cheap to detect — treat as correlation input only                                                              |

Implement ranks 1–4; they are pure computation over a JSON payload your client already can produce, with no third-party dependency and no user-visible effect.

## 4. Automation frameworks and CDP leaks

### 4.1 The CDP signal, precisely

The core technique, published June 2024 by DataDome's Eloi Bahuet / Antoine Vastel, is this: a CDP client that has sent `Runtime.enable` causes the browser to emit `Runtime.consoleAPICalled`, which forces **serialisation** of logged objects across the WebSocket. Chrome otherwise _buffers_ console messages. So a page can plant a trap that fires only when serialisation happens:

```js
var detected = false;
var e = new Error();
Object.defineProperty(e, "stack", {
  get() {
    detected = true;
  },
});
console.log(e);
// detected === true  ⇔  a CDP client with Runtime.enable is attached
```

`Error.prototype.stack` is the one property V8 formats _lazily, on access_, so a getter on it is honoured during CDP serialisation but not during ordinary logging. DataDome notes the obvious false positive — a real user with DevTools open — and the obvious counter — bot authors launching with `--auto-open-devtools-for-tabs` to look like a developer. They also note the timing trick that separates the two: [`brotector.js` L143](https://github.com/kaliiiiiiiiii/brotector/blob/master/brotector.js) distinguishes CDP from the DevTools _UI_ by timing.

Rebrowser's independent reproduction is worth quoting because it is the strongest evidence the signal is _actually deployed_, not just publishable: on Cloudflare-Turnstile- and DataDome-protected sites, "major automation libraries fail … even when running on a real computer with a perfect residential IP," and "then we tried to disable Runtime.Enable in playwright and puppeteer libraries, and the captcha request disappeared with all the same other conditions."

The pattern across every entry: **the fix moves the leak, it does not remove it.** Rebroswer kills `Runtime.enable` and adds a `sourceURL` tell. Patchright kills Console and adds a Route-rewrite timing tell. Camoufox kills CDP and inherits a Firefox engine dialect. A defender who writes _one_ detector gets beaten in a quarter; a defender who writes a **consistency lattice + timing side-effect battery** (§3.2, §4.3) gets beaten only by an attacker willing to maintain a patched browser _and_ a fingerprint generator _and_ per-version API models.

### 4.3 The timing side channels available to you for free

You do not need `Runtime.consoleAPICalled`. Several signals are observable from ordinary server + client telemetry:

1. **Navigation latency decomposition.** `PerformanceNavigationTiming` gives `connectStart/connectEnd/requestStart/responseStart`. Patchright's Route-rewrite init scripts and any HTML-rewriting injector add measurable, _self-referential_ skew between `responseStart` and the first script execution. You are looking for a bimodal distribution, not an absolute.
2. **First-paint-to-first-JS-execution gap.** Camoufox uses `--no-css-animations` (`instantAnimations`) by its own admission; forcing `animationend` instantly is a timing anomaly.
3. **Input event shape.** Camoufox's `wheel-native-ticks` patch exists because wheel `deltaY` values from automation have a characteristic non-native granularity — a native physical wheel produces specific tick patterns. `mousemove` events with `movementX === 0` on every event, or with perfectly uniform timestamps, are the naive version; Camoufox specifically replays 2,356 recorded human trajectories (Cursory) _with the recording's own timing including pauses and overshoots_, which defeats naive kinematics checks.
4. **`Input.coordinatesLeak`-style artefacts.** Dispatch a synthetic event and check whether the browser's own internal coordinate bookkeeping reveals an external driver.
5. **CDP-window timing.** If you can afford an anomalous probe on a challenge endpoint, the `Runtime.enable` window itself is measurable — cloud browsers like Rebrowser advertise exactly this as a feature ("notifications if your library uses `Runtime.Enable` during execution").

## 5. Behavioral biometrics that survive reset

### 5.1 Why behaviour is the strongest residue

The most recent measurement in this area is the most damning for browser-fingerprint-only defences:

> **FP-Agent** (Wang, Shafiq, Vekaria; arXiv 2605.01247, May 2026). First controlled measurement of **seven AI browsing agents** plus human users on an instrumented honey site across three tasks (flight booking, shopping, forum interaction). Browser fingerprints gave **limited** discriminative power when shared across agents. **Behavioural** fingerprints — typing, scrolling, mouse — separated agents from humans _and from each other_. In a case study against Cloudflare's bot detection, **FP-Agent detected all seven AI browsing agents; Cloudflare detected one.**

This is the 2026 restatement of a structural fact: engine-level spoofing is now good enough that the _client description_ is a weak signal, and the _motion_ is where the residual lives. Camoufox's own cursor mode is the attacker's answer, replayed from real recordings — so the bar is now "replay real human kinematics," not "make Bézier curves."

### 5.2 Accuracy claims, and what they cost

Honest numbers, with sources:

- **Keystroke dynamics, 2025 SOTA-ish:** `LGBM` binary classification reached best performance at **80% F1-score** with lowest FRR and EER means on a purpose-built dataset (Springer, _Discover Applied Sciences_, Aug 2025, DOI 10.1007/s42452-025-07449-5, KeyRecs dataset). 80% F1 on a _lab_ dataset with cooperative subjects is not a deployable authentication factor.
- **Keystroke dynamics as a field:** a 2025 ACM Computing Surveys treatment (DOI 10.1145/3733103) documents decades of work; the recurring finding is that per-user models are needed and cross-user transfer is poor.
- **The falsification problem:** _Adaptability of current keystroke and mouse behavioral biometric systems: A survey_ (Computers & Security, Oct 2025, DOI 10.1016/j.cose.2025.104731) states the operational problem directly — because these systems analyse behaviour, **"changes in behaviour can cause a rise in false positives, making the current approaches less effective."** For a Quran reader, the behaviour changes when a user is: tired, injured (one-handed), praying (rapid, repetitive, deliberately similar input), travelling, on a new keyboard, using a screen reader, or simply reading rather than typing.
- **Statistical attacks:** _Revisiting the Security of Biometric Authentication Systems Against Statistical Attacks_ (ACM TOPS, DOI 10.1145/3571743) shows behavioural biometrics' uniqueness has been challenged by attacks that infer general population statistics and then target a specific victim. Behavioural biometrics are therefore weak _both_ ways.
- **Privacy friction is a first-order blocker, not a footnote.** Anatomy of the problem:
  - **GDPR Art. 9(1)** prohibits processing of "biometric data for the purpose of uniquely identifying a natural person" absent an Art. 9(2) exemption — explicit consent being the only realistic one for a consumer app ([gdpr-info.eu/art-9-gdpr](https://gdpr-info.eu/art-9-gdpr/)). Keystroke and mouse dynamics are _behavioural_, not physiological, so whether they qualify as "biometric data" under Art. 4(14) is arguable — but arguable is an expensive word for a small team.
  - **ePrivacy Art. 5(3)** independently requires consent for storing information on, or gaining access to information stored in, a user's terminal equipment. The EDPB's Guidelines 2/2023 on the technical scope of Art. 5(3) treat device fingerprinting as within scope. `[pointer, unverified — EDPB guideline PDF was not fetchable from this environment; verify before relying on it]`
  - **EU AI Act Art. 5(1)(f)** prohibits AI systems that **infer emotions** in the workplace and in education institutions, with narrow medical/safety exceptions, in force since 2 Feb 2025 ([artificialintelligenceact.eu/article/5](https://artificialintelligenceact.eu/article/5/)). A generic consumer app is not in scope, but this signals the regulatory direction of travel: affect inference from behaviour is being fenced off, not opened up.
  - Practical consequence for this project: **do not build a behavioural biometric.** Build server-side _aggregate_ behavioural signals (interval entropy, navigation graph shape, session-consistency) that require no client-side keystroke capture, no Art. 9 consent, and no DPIA fight. See §9 item 6.

### 5.3 The behavioural signals that are cheap and legally clean

All server-side, all from ordinary request logs, none requiring client telemetry:

| Signal                                   | What it catches                                                                                                                                                                                          | Caveat                                                                                                                                          |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Inter-request interval entropy**       | A bot with fixed sleeps has near-zero variance; a human reading Arabic text has high variance and long tail. But Camoufox/Botright replay recorded timing — so entropy alone is defeated by good tooling | Measure per-_session_ variance and compare to the user's own baseline; the tell is a session whose variance matches _another account's_ session |
| **Navigation-graph shape**               | Scrapers traverse sequentially (surah 1→114 or 2:1→2:286) with no revisits and no full-page loads. Readers jump, re-read, search, and bounce                                                             | Power users and offline-caching clients also traverse linearly                                                                                  |
| **Asset-completeness ratio**             | A real browser fetches CSS/fonts/images and issues conditional requests. A scraper fetching JSON gets 100% of content for 5% of the bytes                                                                | API clients are legitimate users; don't punish them — _tag_ them                                                                                |
| **Cache/ETag behaviour**                 | Real browsers revalidate. A scraper ignores ETags and re-downloads                                                                                                                                       | Some HTTP libraries do conditional requests properly                                                                                            |
| **CSRF/nonce/token lifecycle adherence** | Bots sometimes mint tokens they never use or use out of order                                                                                                                                            | Fragile; breaks on bfcache and retries                                                                                                          |
| **RTT jitter correlation**               | Requests through the same residential gateway share a jitter signature. The right framing: **behaviour is a clustering input, not a classifier.** Use it to connect identities; use credentials and resources to confirm.

### 6.2 Graph construction (and why the naive version fails)

The correct data model is a **bipartite/multipartite entity graph**: `accounts × device_tokens × ip_buckets × payment_hashes × behaviour_centroids × registration_cohorts`. Then:

- Naive **exact-match connected components** over-reach: a shared mobile /24 links thousands of unrelated users into one component, and you end up banning a city.
- The working version is **weighted edges + a threshold, then components**. Each edge type carries a weight reflecting its false-positive rate: identical payment hash >> identical device token >> identical canvas+fonts+timezone >> same ASN+/24 >> same time window.
- Compute components only over edges above threshold, then **review components, not accounts**. This is the standard published CIB pipeline (§7) applied one level down.
- Guard against the **amplification attack on your own graph**: an attacker deliberately sharing a resource with victims to poison your clustering (the "ant trap" framing — Castle's _Ant traps, fraud graphs, and the cost of blocking too soon_, [blog.castle.io/ant-traps-fraud-graphs-and-the-cost-of-blocking-too-soon](https://blog.castle.io/ant-traps-fraud-graphs-and-the-cost-of-blocking-too-soon/)). The defence is that edge weights must be _asymmetric_: a single high-precision edge (payment hash) is a strong link, but a single low-precision edge (shared ASN) must never be, no matter how many accounts touch it.

### 6.3 Device tokens: the one lever you actually own

Issue an opaque, HMAC-signed token on first visit, rotate it on a schedule, and **bind it to the account on login**. This is strictly stronger than fingerprinting because:

- You choose the entropy, lifetime, and rotation policy.
- It cannot be "spoofed consistently" — the attacker must either present the token (linkage) or present a missing/foreign token (a signal).
- It is _not_ a fingerprint under ePrivacy/GDPR if it is a first-party session/anti-abuse identifier with a stated purpose and a retention limit. It becomes one if you use it to build a cross-site identifier.

Design notes: sign it, don't encrypt it (you want it opaque and verifiable, and you don't want to be a PII store); store the _set_ of tokens per account, not one, so you can see account-token fan-out in both directions; and expire aggressively.

### 6.4 Payment-instrument hashing: what to do and where the line is

**Do:** store a **keyed** cryptographic hash (HMAC) of the payment instrument identifier your PSP exposes — Stripe's `card.fingerprint`, Adyen's recurring detail reference, or a token your processor returns. Never store or hash the PAN yourself; never store the CVV under any circumstance.

**Why hashing is the right primitive and not a privacy fig leaf:** PCI DSS accepts one-way cryptographic hashing — with a key — as a method of rendering a PAN unreadable when displayed or stored, which is why "card fingerprint" exists as a first-class PSP concept. That also means the hash is _linkable by design_, which is exactly what you want for fraud linkage and exactly why it must be protected.

**Where the ethics/legal line sits** (this is the part threat models usually skip):

1. **A hashed PAN can still be personal data.** Under GDPR, pseudonymisation (Art. 4(5)) reduces risk but does not remove the data from scope; recital 26's "reasonably likely to be used to identify" test is about the means available, not the format. Treat card-hash linkage as processing personal data with a DPIA, a retention period, and a stated purpose.
2. **Purpose limitation is the binding constraint, not technique.** Using a card hash to detect a fraud ring on _your_ platform: defensible. Using it to build a cross-merchant identity, to feed ad targeting, or to score a user for anything beyond anti-abuse: not defensible under the stated purpose, and not defensible in public.
3. **No PII overreach.** Correlate _hashes_, never names/addresses/emails beyond what is required to action a specific case. In particular: do not build a shadow profile of a user's device graph and then expose it to third parties. If a human reviews a cluster, review the cluster's _evidence edges_, not a dossier.
4. **Proportionality and the false-positive duty.** Every linkage signal has a false-positive cost paid by a real person, and on a small app that person is a volunteer or a donor. Design the response ladder so that a wrong linkage produces _friction_, not _exclusion_ (§9 item 8). Rotten Tomatoes and Valve both solved this by scoping what counts — verified-purchase-only reviews, and excluding entire time windows from the score rather than deleting reviews ([Wikipedia, _Review bomb_](https://en.wikipedia.org/wiki/Review_bomb)).
5. **Symmetry of knowledge.** If you are going to link accounts, say so in plain language in your privacy notice, in the reader's language. A Quran app that quietly fingerprints its readers has a worse problem than the bots.

## 7. Coordinated inauthentic behaviour at scale

### 7.1 Platform practice (what to imitate)

**Meta** publishes semiannual Adversarial Threat Reports and maintains a full archive back to 2017 ([transparency.meta.com/metasecurity/threat-reporting](https://transparency.meta.com/metasecurity/threat-reporting/)). Three things about how they frame it are directly copyable:

1. **Enforcement is on behaviour, not content.** The Q2–Q3 2025 report states: "CIB involves coordinated networks of Meta assets working together to mislead people using false identities. Our enforcement of CIB violations is based on the deceptive behavior these networks engage in, and not the content they post." For an app serving religious content, this is the difference between moderating _what a user says about Islam_ (a free-speech minefield, and not your job) and moderating _whether the account is a real distinct person_ (a technical, defensible question).
2. **Scale reclaims the narrative.** Q1 2025 covered three networks from China, Iran and Romania in one quarter, the Romanian operation alone ~20,000 accounts and ~$177,000 ad spend — that is **~$8.85 per account**, which is the actual unit cost of the abuse you are defending against. If your signup friction costs an attacker more than ~$9 per account, you have changed their economics.
3. **They now report AI in every network.** By H2 2026 Meta reports "AI technologies are now present in the operations of virtually every CIB network we disrupt," and that an Iranian network targeting US audiences was disrupted in Q4 before it built an authentic audience.

**OpenAI** publishes case-study-level disruption reports, with a detect → investigate → disrupt → disclose process, and a demonstrated willingness to say _how_: "Disrupting a new covert influence campaign from Russia" (Aug 2026), a Cambodia-based criminal scam operation (Jul 2026), the "Tech and Tariffs" campaign (Jun 2026), and an explicit "false front" operations writeup (Oct 2026) ([openai.com/index/disrupting-malicious-uses-of-ai](https://openai.com/index/disrupting-malicious-uses-of-ai/)). Two of these are directly relevant: the **"false front"** framing is the pattern for fake Quran/Islamic-content accounts, and the combos of AI-generated profile text plus coordinated posting is now the default, not the exception.

**Google TAG** publishes through Google's security blog; the legacy `blog.google/threat-analysis-group/` path now redirects to `blog.google/security/` `[pointer, unverified as a report index]`. TAG's pattern is technical attribution plus coordination with other platforms — which is only useful to you if you are willing to publish.

**EU DSA transparency database** is the highest-value public artefact most defenders ignore: 4.35 billion statements of reasons from 375 platforms, with a Research API and bulk download, exposing restriction types, automated-decision share (**41% of decisions are fully automated**), and the most-cited violation types ([transparency.dsa.ec.europa.eu](https://transparency.dsa.ec.europa.eu/)). You can check your own enforcement patterns against 375 platforms.

### 7.2 The published detection pipeline (and its numbers)

The recurring academic/industry pipeline:

1. Collect posts/actions around a narrative.
2. Link accounts performing the **same action** within a short window — co-retweet, co-link, co-hashtag-sequence, identical text.
3. Project the bipartite action graph into an account-to-account network.
4. **Drop weak edges** — published pipelines use 10–60 second windows and keep only the top ~1% of edge weights, or apply a statistical backbone test.
5. Run **community detection** (Louvain) or connected components.
6. **Review each dense community by hand.** Deciding a community is _inauthentic and harmful_ is a human judgement; the algorithm only finds the coordination.

Tooling that exists and is used: **CooRTweet** (R; default 10-second window, min 2 participations), the **QUT Coordination Network Toolkit** (Python; 60-second window; six network types including co-retweet and co-similarity), Gephi + Louvain, and NetworkX/igraph. Note that **Botometer runs archival-only since June 2023 and cannot score accounts created after that date** — do not build on it.

Academic state of the art, for calibration:

- _Coordinated Inauthentic Behavior on TikTok: Challenges and Opportunities for Detection in a Video-First Ecosystem_ (ICWSM 2026, DOI 10.1609/icwsm.v20i1.42711) — video-first platforms change the feature set.
- _EDCOC: Early Detection of Coordinated Online Community Using Graph Neural Networks_ (DOI 10.1007/978-3-032-13509-4_26) — GNNs for _early_ detection, i.e. before the campaign has an audience.
- _Detecting Coordinated Inauthentic Behavior in Likes on Social Media: Proof of Concept_ (arXiv 2305.07350) — engagement-only coordination is detectable without any content analysis.
- _Coordinated inauthentic behaviour on Facebook? A typology of manufactured attention_ (Rogers & Righetti, Sage, 2025) — useful taxonomy for naming what you are looking at.

### 7.3 What a small self-hosted app should actually compute

You have none of the above infrastructure and do not need most of it. The minimum viable version:

**Inputs:** account creation events, device tokens, ASN buckets, signup bursts, review/rating events if you have them, and — critically — **the request-interval and navigation templates** you already log.

**Computation:**

1. Two-minute (not ten-second) buckets. Your platform is small; coordination will be visible against a low base rate. Long windows reduce false positives from normal diurnal spikes.
2. Co-action edges with a per-window count.
3. Backbone filter: keep only the top 1% of edge weights, or apply a simple binomial surprise test against the expected co-occurrence rate for that pair's activity levels.
4. Louvain or plain connected components over the surviving edges.
5. Emit a **cluster report**: member accounts, edge evidence, total account age, total spend, whether any member has a payment hash. Human review of clusters.

**Why this survives T3:** clustering does not require any individual signal to be unforgeable. A coordinated network can give every account a perfect fingerprint and a distinct residential IP. What it cannot easily do is give every account a _different_ timing template, a _different_ behavioural centroid, and _no_ shared resources, while still acting in a coordinated way — coordination is the very thing you are measuring.

## 8. Against Quran / Islamic-content apps specifically

### 8.1 Honest answer on evidence

**I found no public threat report, incident writeup, or academic study documenting attacker campaigns against Quran apps or Islamic-content platforms.** Searches of arXiv (query `"Quran" AND ("scraping" OR "religious content")` → **0 results**), OpenAlex (2022–2026, Quran mobile app / reviews → 0 relevant works), and Hacker News (`quran app`, ranking by points) returned nothing describing an attack campaign. This is a genuine gap, not a search failure, and it should be recorded as such in the threat model. Absence of reporting is not absence of incidents: religious-community apps are small, unmonitored, and rarely have a security function to write anything up.

What _does_ exist, and what it tells you:

1. **Platform-level removal of Quran apps is real, and driven by state pressure, not attackers.** Apple removed religious apps including a popular Quran app in China in 2021 at the request of Chinese regulators ([BBC News, technology-58921230](https://www.bbc.com/news/technology-58921230); [TechCrunch, 2021-10-15](https://techcrunch.com/2021/10/15/apple-removes-a-popular-quran-app-in-china-after-request-from-local-regulators/)). The threat to a Quran app's _availability_ has historically come from app-store policy and geopolitics, not from abuse.
2. **Reporting mechanisms are a live attack surface against religious apps.** In October 2025 F-Droid incorrectly flagged **Bible and Quran apps as NSFW** — a 180-comment Hacker News thread, and F-Droid's own forum thread titled "NSFW flag incorrectly added to Bible and Quran apps" ([forum.f-droid.org/t/…/33401](https://forum.f-droid.org/t/nsfw-flag-incorrectly-added-to-bible-and-quran-apps/33401)). Whether that was error or malice, it is a working demonstration that a small, volunteer-run religious app's distribution can be obstructed by _misuse of a reporting channel_ at near-zero cost. Assume app-store and directory report-bombing is the most likely hostile action against a Quran app in app stores.
3. **Template attacks from comparable content platforms, ranked by likelihood for your case** (see §8.2).
4. **The same-week evidence that community-targeted review campaigns are a real, organised tactic:** Wikipedia's _Review bomb_ article documents a campaign in which one-star reviews of Gabrielle Zevin's _Tomorrow, and Tomorrow, and Tomorrow_ said "Zionist author," several appearing **before the book was released**, and other Jewish authors reported being "on a list with other Jewish authors on TikTok." ### 8.3 The specific structural asymmetry for a Quran app

The Arabic text is immutable, public, and _must_ be freely distributable — the project's own hard rule ("Quran databases are all immutable") is correct and also means **content-scraping defences are self-defeating if taken too far**. The defensible assets are therefore not the text. They are:

- **the translation/tafsir corpus and its editorial layer**, which has real production cost and licensing;
- **the reader's identity and their reading history**, which is what a device fingerprint is actually protecting;
- **the community layer** (accounts, ratings, contributions), which is where both abuse _and_ the value of the app live.

So the threat model should spend its budget in that order: community-layer abuse first (cheap to defend, high impact), identity-layer second (device tokens + credentials), text-exfiltration last (accept it, and make the legitimate path faster than the illegitimate one).

## 10. Top 8 countermeasures, ranked by impact ÷ implementation cost

Ranked for a self-hosted stack: Rust backend, Svelte reader, no anti-fraud vendor, small team, a global audience including mobile/CGNAT users.

**1. Per-credential and per-API-key rate limits; IP limits as a secondary ring.**
_Impact H / Cost L → highest ratio._ Per-IP counters are exactly what an attacker with a residential pool defeats for free. Per-credential counters are not. Ten lines of state and a token bucket. This also fixes credential stuffing, the highest-value attack in §9.

**2. A first-party device token: issue on first visit, sign with HMAC, bind to the account on login, expire.**
_Impact H / Cost M._ The only linkage signal you fully control. It gives you device-token fan-out (one device → many accounts) and account fan-out (one account → many devices) with no fingerprinting, no third-party script, and a clean privacy story if you keep the purpose and retention narrow.

**3. Fuzzy fingerprint-subset matching stored as a bounded similarity, not a hash.**
_Impact H / Cost M._ FP-Inconsistent's core finding — geometric mean evasion reduction of ~48% — came from _consistency and overlap_, not from new fingerprint entropy. Concretely: store a small set of coarse, high-cardinality-but-stable attributes (WebGL renderer class, font-list digest, screen+DPR, timezone, `Intl` locale chain, voice-count bucket), and match on **subsets with weights** so that "same canvas + WebGL + fonts + timezone, different UA and IP" links, as published multi-accounting systems do. Never exact-match, never single-attribute.

**4. Space-and-time consistency rules over the client payload (the FP-Inconsistent method, applied to whatever the client already sends).**
_Impact H / Cost M._ No new client code: mine rules over the fingerprint your client already reports — pairs of attributes that never co-occur in real traffic, and single attributes that change within a session when they never should. This is the countermeasure with the best independent evidence of efficacy and the lowest dependency footprint. Rebuild the rule set quarterly.

**5. A cheap, published bulk-data path — and make it _faster_ than scraping.**
_Impact M / Cost L._ You cannot stop the scrape of a public text and should not try. You can make the honest path the fastest path: a documented, versioned bulk download or an API key with a generous quota and a clear attribution requirement. This converts a hostile anonymous scraper into an identified, contactable consumer of your data, and removes the motive to run stealth tooling against you at all.

**6. Server-side behavioural _edges_ only: interval entropy + navigation-graph template + asset-completeness ratio, per session, compared to the account's own baseline.**
_Impact M / Cost M._ No keystroke capture, no mouse telemetry, no client biometrics — therefore no Art. 9 consent, no DPIA fight, and no AI-Act emotion-inference exposure (see §5.2 and row 14 of §9). Derive all three from request logs you already have. Use them as graph edges, never as standalone verdicts — FP-Agent shows behaviour is discriminating, and Camoufox shows it is replayable.

**7. A weighted entity graph over `accounts × device_tokens × ASN-buckets × payment_hashes × registration-cohorts`, with thresholded components and cluster-level human review.**
_Impact H / Cost H._ The only thing that scales to T3, and the only thing that survives perfect per-account fingerprint spoofing — because it measures _coordination_, not _identity_. Build it late, build it small, review clusters not accounts, and use asymmetric edge weights so that a low-precision shared resource (a mobile /24) can never accumulate into a ban. This is where the Meta/X/Academic CIB pipeline lands in a stack your size.

**8. A progressive response ladder: throttle → challenge → step-up → restrict → review. Never hard-block on a single signal.**
_Impact M / Cost L._ The cheapest item on this list and the one that determines whether the other seven are net-positive. Rotten Tomatoes' and Valve's review-bomb solutions both work by _scoping and deferring_, not by deleting. Cloudflare's 4-in-5 number is the reason: on a Quran reader your false-positive population is disproportionately the people the app exists to serve — mobile users, CGNAT users, users on low-end devices, users behind national filters, and Tor users in jurisdictions where reading is risky. Set the ladder so that a wrong decision costs a real user a second, and a hostile actor a dollar.

**Explicitly not recommended:** buying a bot-management vendor at this size (FP-Inconsistent measured ~45–53% evasion against two of the best); any behavioural-biometric authentication; blocking by ASN or by residential-IP reputation; a raw public user-rating score; keeping Quran text SHA-256s in any automated path (this project already forbids it, correctly — a DB's identity is its id).
