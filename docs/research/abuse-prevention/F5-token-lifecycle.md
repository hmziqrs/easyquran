**One-line verdict.** The token's _identity_ design (server-minted, HMAC-stored, evidence-only) survives
this pass. Its _lifecycle_ does not exist yet: four of the five transitions are unspecified, rotation on login
would be a race with no benefit, and the single most
important lifecycle rule — **a second account on the same browser must add a link row, never reassign
an owner column** — is the exact inverse of the only device-token lifecycle the repo already ships
(the FCM `devices` table, which _tests_ reassignment as correct). Twelve findings, all NEW.

## 0. Scope note, and the one thing the repo already proved

The target is the Option B token: server-minted ≥128-bit opaque value, `HttpOnly; SameSite=Lax; Secure;
Path=/api` cookie `ruxlog.device` (B1 §7a), bound at login, **never an auth factor** (DESIGN-v1 B4,
A9 §3.2, C1 §4.1), **never the sole cause of a ban** (DESIGN-v1 B1, B5 P2). No component fingerprint,
no `device_key` cohort digest, and no `device_bans` in v1 (B9 F1: no consumer); if a device ban is ever added it
keys on `device_record_id` and pins the record (§2.3).

The repo's FCM push token is the only shipped "device token" lifecycle, and it is a _negative_
precedent for this feature:

| FCM `devices` behaviour                                                        | Where                                                                                                       | Why it is wrong for the device token                                                                                                                   |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `UNIQUE(token)` global; re-register **updates `user_id`** on conflict          | `device/actions.rs:21-34` (`OnConflict::column(Column::Token).update_columns([UserId, …])`)                 | one row per token means the second account **erases** the first account's ownership — the linkage asset is destroyed by the very event that creates it |
| reassignment is a **pinned test**                                              | `device_v1/controller.rs:167-193` (`registering_same_token_transfers_ownership_without_duplicate_delivery`) | the transfer is intended, documented behaviour; copying it into the evidence table reproduces the failure                                              |
| migration **deletes** multi-owner tokens and collapses duplicates to `MAX(id)` | `m000011:11-19`                                                                                             | history is destroyed by migration as well as by runtime; the token layer must never have an equivalent statement                                       |
| `ON DELETE CASCADE` to `users`                                                 | `m000005:21-22`                                                                                             | user deletion destroys the row; the evidence layer must not inherit the FK (C2 §6 item 7, B8 F12)                                                      |
| oldest-evict past `MAX_DEVICES_PER_USER = 20`                                  | `device_v1/controller.rs:17,20-31`                                                                          | eviction deletes the **oldest row** — for delivery that is correct, for evidence it is data loss                                                       |

Two further repo facts that shape every transition below:

1. **Register creates no session.** `auth_v1/controller.rs:459-535` creates the user, emails a code and
   returns `201`; there is no `cycle_id()`, no `create_bound_session`, no cookie. "Bind at
   login/register" (C1 §7.2 B3) is therefore wrong on the register half.
2. **Every authenticated session in the app goes through one helper.**
   `create_bound_session` (`auth_v1/controller.rs:1115-1174`) is called by log_in, login-totp, passkey
   login and OAuth, and it is fail-closed at every step (audit row → tower save → binding → fresh-auth).
   That helper is the correct and only mint/bind site.

### 1.4 Rotate

| #   | Transition                            | Rule                                                                                                                                                                                                                                                                                                                                                                                             | Evidence / anchor                                                                                                                                                                                                |
| --- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | **On login**                          | **No.** The token is not a privilege, so freshness buys nothing; per-login rotation re-writes `token_hash` on a stable record, and the two-tab case then races (the jar keeps one response's cookie, the row keeps the other response's hash ⇒ unknown device). M4 shows that minting-once makes the double-login benign.                                                                        | B1 §6.3 (no rotation on login). `auth_v1/controller.rs:188-203` (login is a write path where the race lands); extractor `:101,121` (`cycle_id()` per login — the session rotates; the token must not follow)     |
| R2  | **At the 1-year record cap**          | **Yes — in place.** Rotate `token_hash` on the **same** record (same `id`, same `first_seen_at`); set the new cookie in the login response; keep `token_key_id` unchanged. A new record (new ULID) would orphan any live ban; B8 §2.3 rotates in place for the same reason.                                                                                                                      | B8 §2.3 (the re-mint cap), §1.6 D6; B1 §6.3 ("the _record_ is stable")                                                                                                                                           |
| R3  | **On revoke**                         | **Yes, by construction**: a revoked record never returns; the next login mints a fresh record (M3).                                                                                                                                                                                                                                                                                              | §1.5 V3/V4                                                                                                                                                                                                       |
| R4  | **On ban**                            | **No.** Revoking on ban hands the evader a clean slate: the old record (with its links) stops matching, the next login mints a new record with no history. Keep the token live (it grants nothing) so the evader's next account self-incriminates onto the known record; pin the record instead.                                                                                                 | `device_v1/controller.rs:84` (`delete_for_user` — the delete-the-row shape), `m000011:11-19` (delete-the-history shape); B8 §1.3 sweeper ban guard is the pin mechanism                                          |
| R5  | **On logout**                         | **No.** Stated explicitly because a reviewer expects it.                                                                                                                                                                                                                                                                                                                                         | B1 §6.6; `auth_v1/controller.rs:73-118` (logout deletes the tower session + revokes the audit row — the token is not in that path, and cannot be: HttpOnly on `/api`, `purge-hook.ts:19-24` touches caches only) |
| R6  | **On password change / email change** | **No** (considered, rejected). The leak window that rotation would bound is already closed by the record's other controls, and the damage from a leaked token value (link rows) is retained regardless. Adding a third rotation site adds a race without a matching threat. If the owner wants it: the invariant is _rotate in place, same record id, and the response must set the new cookie_. | `user/actions.rs:207-240` (password change already rotates `session_auth_secret`), `:142-154` (email change does too) — the trust-transition sites exist; the token is deliberately not added to them            |
| R7  | **Cookie `Max-Age`**                  | Re-set the **same value** with a fresh `Max-Age=2592000` on every successful login/link, so the cookie's clock tracks the sliding record. This is not a rolling refresh (no per-request write) and not a rotation (the value is unchanged, so M4's race cannot occur).                                                                                                                           | B1 §6.2–§6.3 (no per-request refresh; re-set at login). Without the re-set the record **slides** while the cookie does not, so an active user's identity would reset on day 31 (F7)                              |

**What breaks if it never rotates:** one stable cookie-valued identifier per browser for up to a year,
linked to accounts. Privacy cost (a first-party persistent identifier that must be disclosed in the
policy and is DSAR-visible); theft cost (a leaked value is reusable until revoke/re-mint, but grants no
privilege). Both are bounded by R2+R3 and by `revoked_at` on a reported theft.
**What breaks if it rotates often:** legitimate "new device" churn (Safari ITP already clears storage —
A1 §4e Path 2), a race per rotation, and zero evasion value (clearing storage is free).

**UI design (the surface does not exist today — verified).** What exists: the account page's Sessions
section lists `user_sessions` audit rows with a per-row terminate (`account/+page.svelte:228-274`,
`sessions_terminate` at `auth_v1/controller.rs:1041-1093`); `sessionDeviceLabel` (`account-view.ts:57`)
is the "never leak the raw UA" label precedent; the settings Privacy section shows notifications as a
**read-only status label** (`PrivacySection.svelte:109-114`) — there is no FCM revoke toggle there, and
`POST /device/v1/list` has **zero web callers** (`web/src/lib/firebase/messaging.ts` calls only
`register`/`delete`; grep for `device/v1` in `web/src` finds only that file and its test). So: no device
list, no device revoke, and a dormant list endpoint.

Add a **Devices** section beside Sessions, sourced from U4:

- Row: label derived from `context_last` + platform class (reuse `sessionDeviceLabel`'s discipline), "This
  device" marker, `first_linked_at`/`last_linked_at`, two actions.
- **Remove from this account** (V3) — link-scoped, no confirmation dialog, copy: "This device will no
  longer be linked to your account. Other people who use this browser are not affected."
- **This isn't my device** (V4) — confirm dialog, copy: "This signs the browser out of our records for
  every account that uses it. If you sign in here again, it will be a new device."
- **Never show a fan-out count to the user** ("3 other accounts use this browser") — that leaks account
  existence to co-users on a shared phone. Only the operator sees fan-out (U5).
- Auth: session + CSRF (`static_csrf.rs:88-141`), rate-limited per user (~10/day), **no fresh-auth**
  (revoking a device is not a credential change; `fresh_auth::consume` would add friction to a privacy
  control — contrast `user_v1/controller.rs:117`).
- Empty state ("We don't recognize this browser") must not read as an error: unknown is the baseline.

### 1.7 Abuse, and what the design does about each

| #   | Attack                                                                          | Design response                                                                                                                 | Residual                                                                                                                                                                                                                                                                                                          |
| --- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | **Token theft** (XSS in-place, malicious extension, shared computer, proxy log) | HttpOnly removes read-and-transfer by page scripts (B1 §3); the token gates no privilege, so theft cannot take over an account. | The thief can **use** the token in place and **bind the victim's record to attacker accounts** ⇒ attribution poisoning (§1.8 C1). Extensions can read HttpOnly cookies via `chrome.cookies`; HttpOnly is not a boundary against them. Mitigation is §1.9 S1 + typed edges + self-clearable friction, not secrecy. |
| A2  | **Token sharing to implicate someone else**                                     | Sharing your own token moves _your_ linkage to the recipient — it implicates you.                                               | The real framing vector is the reverse: use a _victim's_ browser (shared computer, extension, XSS) so the victim's record gains edges to attacker accounts. Same mitigation.                                                                                                                                      |
| A3  | **Token farming** (fresh profile per account)                                   | The mint requires an authenticated login; a fresh profile gets a fresh token for free.                                          | ~No cap. The control is per-account **new-link** counting as a review trigger (§1.9 S2), never a block.                                                                                                                                                                                                           |

## 2. Three schema decisions this pass changes

### 2.1 The link table replaces the owner column as the evidence edge

`device_records.user_id` survives as a display cache; `device_account_links` is the edge (B1/B2/B3).
This is the difference between "who owns this token now" (FCM semantics, reassignable) and "who has
used this browser" (evidence semantics, append-only per pair).

### 2.2 `device_sessions` is dropped from the Option B schema

C2 §6's merged mDDL carries `device_sessions` (record × session × user). In Option B it buys nothing the
link table plus `user_sessions` do not already answer, and it is a second retention surface:

- "which account did this on the kiosk" (B5 §2.4c) → the link table at account granularity; the write's
  own audit row gives the session.
- "sessions per device per day" (B5 F1's shared-account detector) → an on-demand admin join against
  `user_sessions` (`user_id`, `last_seen`), not the request path.
- The `device_key` cohort queries that motivated it do not exist without a fingerprint.
  This is a deliberate divergence from `B5-shared-devices.md` §2.4(c) and `C2-contradictions.md` §6, stated
  so the next reader does not "restore" the table by habit.

### 2.3 The ban key is `device_record_id`, and the ban pins the record

The ban key is `device_bans.device_record_id` + the pin (D3), as in B8 §1.1 — never the fingerprint digest,
which Option B does not have. This is the whole resolution of the 30d-vs-12mo conflict for this variant (F6).

## 3. Attacker's playbook (step by step), and what the design must add

1. **Recon.** The design is public: the token is an `HttpOnly`, `Path=/api` cookie, evidence-only, not a
   privilege, and it lives in `device_account_links`. Attacker knows the token cannot log anyone in.
2. **Farm identities.** N accounts, one fresh browser profile each (or clear cookies between signups) ⇒
   N tokens, N records, N links. Cost = captcha + inbox. _Design must add:_ nothing on the token side
   (this is A-side admission control, C1 §3.4); the per-account new-link count (§1.9 S2) makes the farm
   _visible_, not blocked.
3. **Get a victim's token in place.** Shared/library computer, a malicious extension (`chrome.cookies`
   reads HttpOnly), or XSS on the origin (the CSP trusts `gstatic`/`googletagmanager`/
   `challenges.cloudflare.com` — B1 §3, C2 §8). The token cannot be exfiltrated by page JS, but it can be
   **used** by any script running on the origin, and read by an extension.
4. **Poison the victim's record.** Using the victim's browser, log into attacker-controlled accounts.
   Each login adds a link row: _victim's record → attacker accounts_. Then get one attacker account
   banned. The victim's browser now carries a "linked to a banned account" edge.
   _Design must add:_ (a) the record is never the sole cause of any effect (already the rule); (b)
   `trust_state` may only ever produce a self-clearable L2 challenge, never a ban, never a quota
   (§3.9 F9); (c) the operator sees the **edge type** ("same token") separately from "same account" and
   "same IP", and needs a second admissible corroborator (B5 §5.1 step 3, B9 F11).
5. **Frame a victim's account.** Lure the victim to log in on an attacker-controlled browser ("free
   Wi-Fi", a friend's laptop, a demo machine). The victim's _account_ gains a link to a record the
   attacker later abuses from. _Design must add:_ the same as step 4 — plus the link row must never be
   readable by the account owner as "your account is linked to device X" in a way that leaks the
   attacker's other accounts.
6. **Evade by clearing.** Clear storage between accounts. The record stops matching; the next login is a
   fresh unknown device. _Design must add:_ nothing (accepted residual); do not punish absence — the
   moment "unknown" costs friction, every privacy clearer and every ITP eviction becomes a false
   positive (A1 §4e Path 2).
7. **Evade by staying on the token.** Keep the token, never clear, use a second account. The record
   accrues the second link. This is the product working.
8. **Replay a stolen token elsewhere.** Present the cookie value from another machine: the record
   matches; the attacker's machine now looks like the victim's browser (step 4's variant). _Design must
   add:_ the revoke path (V9) must be reachable by the victim ("this isn't my device" on the device list)
   and must be honest that it erases the past, not the future (a new record is minted on next use).
9. **Flood the queue.** Emit links from cheap identities on one record so the operator's case view shows
   a huge fan-out. Cost ≈ zero; the operator's time is the target (B9 F4). _Design must add:_ the panel
   cap (20), cohort collapse, and the rule that fan-out is a _shared-device_ signal that steps down and
   bars L6 — i.e. the flood **cannot** produce a ban.
10. **Destroy the linkage by making the operator distrust it.** If the operator learns the linkage is
    mostly shared-device noise, the feature is dead. _Design must add:_ the two zero-tolerance metrics
    (proposals from shared devices = 0; challenge rate on granted devices = 0 — B5 §8) and the
    claim-after-ban rate, so the noise is measured rather than argued about.

**What the design must add, condensed:** (1) link rows not owner columns; (2) evidence-only, second
corroborator, typed edges; (3) `trust_state` can never ban and is always self-clearable; (4) no
challenge from absence — flagged-only, writes-only; (5) never revoke on ban; pin the record; (6) the
revoke UI with two honest verbs; (7) case-scoped, audited admin reads; (8) the shared-device guards
(B5 §2/§3) as a _shipping prerequisite_, not a follow-up.

## 4. Legitimate shared-device user's playbook, and what must not break

1. **Family phone, three accounts, one browser.** Dad logs in (mint record R + link Dad). Mom logs in
   (no mint; link Mom on R). The kid logs in (link Kid on R). One token, one record, three links.
   _Must not break:_ no prompts, no challenges, no "new device" notice for Mom or the kid (M5 must not
   be treated as an anomaly anywhere). `device_records.user_id` flips to whoever logged in last — and
   **nothing reads it** (B3).
2. **One of them logs out.** The record and the other two links are untouched (V1).
3. **One of them is banned for something they did.** The ban is on the account (`user_bans.user_id`);
   the record is **not** revoked, **not** banned, **not** flagged for the others (V6, B5 P1/P4). The
   other two accounts keep working, keep their sessions, keep their device list entries.
4. **The kid deletes their account.** The kid's link row is deleted; Dad's and Mom's links survive; the
   record survives (D4).
5. **They click "This is a shared device"** (B5 §3). The record's reputation clears for 30 days, prompts
   stop for everyone on it, and **no account's ban is affected** (B5 §3.2).
6. **They clear the browser / get a new phone.** New token, new record; the old one ages out; nobody is
   challenged and nothing is punished (S1/S2, A5).
7. **Dad clicks "Remove from my account".** Mom's and the kid's device list entries are untouched; the
   record survives for them (V3).
8. **They compare screens.** Neither sees the others' accounts, nor a fan-out count, nor a "3 accounts
   use this browser" hint (V3/UI rule).
9. **They are on a madrasa kiosk** (B5 §7): per-student accounts, one enrolled device, prompts
   suppressed for everyone, no ban propagation, the grant bound to the record not to any minor's session
   (B5 §7.4).

**What must not break, condensed:** no friction from being shared; no propagation of one account's ban;
no cross-user disclosure in the device list; logout/account-switch/account-deletion on one account must
leave every other account's device identity intact; the self-claim must clear device reputation without
touching `user_bans`.

## 5. Findings (12, all NEW)

### F1 — The bind transition's default (single owner column) reproduces the FCM reassignment, which the repo pins as _correct behaviour_; the link table must be the evidence edge

**Severity: High. NEW.**
**Evidence.** `src/db/sea_models/device/actions.rs:21-34` — `upsert` uses `OnConflict::column(Column::Token).update_columns([UserId, Platform, UpdatedAt, LastSeenAt])`: the second account **overwrites** the first account's ownership on the single row. `src/modules/device_v1/controller.rs:167-193` — `registering_same_token_transfers_ownership_without_duplicate_delivery` asserts the transfer. `migration/src/m000011_device_token_ownership.rs:11-19` — the migration _deletes_ every multi-owner token and collapses duplicates to `MAX(id)`. `C2-contradictions.md` §6 merged DDL carries `device_records.user_id … ON DELETE SET NULL` and no link table. B5 §1.1 cites the transfer as "shared devices are already explicitly non-suspicious" — true for delivery, fatal for evidence.
**Fix.** `device_account_links(device_record_id, user_id, first_linked_at, last_linked_at, link_count, first/last_ip_unit, revoked_at, expires_at)` with `UNIQUE(device_record_id, user_id)` and CASCADE from the record; bind is an UPSERT on the **pair** (B2). `device_records.user_id` becomes a last-owner display cache read by nothing. Guard test: `second_account_on_same_token_adds_link_and_first_link_survives` — assert two rows, `first_linked_at` of row 1 unchanged, `device_records.user_id` not read by the panel query.

### F2 — The only client-side device-lifecycle code in the repo tears the device down on every account change; the token must not inherit that pattern

**Severity: High. NEW.**
**Evidence.** `web/src/lib/stores/notifications.svelte.ts:98-103` (owner change ⇒ `#queueTeardown(stored.token, stored.ownerId)`), `:107-134` (`onAuthChanged` tears down on logout **and** on account switch, then re-registers for the new owner), `:151-156` (`unregisterTokenFromServer` + `deleteFcmToken`); `web/src/lib/firebase/messaging.ts:136-168` (`register`/`delete` with `expected_user_id`); `src/modules/device_v1/controller.rs:77-86` (`delete` removes the row). For FCM that is correct (one delivery owner). For the evidence token it is the exact inverse: the account switch is the event that **creates** the cross-account edge.
**Fix.** The device token is a server-set cookie with **no client lifecycle code at all**: no `web/src/lib/device/**` register/delete calls, no `easyquran.device` localStorage key (contrast the FCM `easyquran.fcm` record at `notifications.svelte.ts:22`). Guard (raw-source, the B1 §7c-2 pattern): no device-layer file matches `unregister|deleteToken|ownerId`, and `messaging.ts`'s device endpoints are untouched by the new module.

### F3 — Rotating the token on login would be a race with no benefit; rotation has exactly two triggers

**Severity: Medium-High. NEW.**
**Evidence.** `crates/rux-auth/src/session/extractor.rs:101,121` (`cycle_id()` on every login — the session rotates per login; the token must not follow it, or a two-tab login writes two different `token_hash` values onto one record while the browser keeps one cookie, and the loser's next request is an unknown device). `src/modules/auth_v1/controller.rs:188-203` (the login path where the write would land). A9 §3.2 (the token is not an auth factor ⇒ freshness buys no security). B1 §6.3 states the same rule; `B1-F7` warns "token rotation ≠ record rotation".
**Fix.** R1/R2/R3: **no** rotation on login; rotation **only** at the 1-year cap (in place, same record id) and on revoke. Mint-once makes the double-login benign (M4: at most one phantom record, no hash overwrite, the presented cookie always matches its own record). If a rotation race ever becomes unavoidable, the fix is a bounded token history (`token_hash_prev`, `token_hash_prev_expires_at`, ~5 min), not a per-login write.

### F4 — The design's "bind at login/register" is wrong at both ends: register has no session, and the anonymous bootstrap paths must never mint

**Severity: Medium. NEW.**
**Evidence.** `src/modules/auth_v1/controller.rs:459-535` — `register` creates the user, spawns the verification mail and returns `201`; no `cycle_id()`, no `create_bound_session`, no cookie. `C2-contradictions.md` §7 (item 7) — `web/src/lib/auth/auth-client.ts:231-260` makes `POST /csrf/v1/generate` the first unsafe call for every anonymous visitor, and `csrf_v1/controller.rs:10-25` mints an anonymous session there; `GET /user/v1/get` fires on page-load hydrate. `src/middlewares/static_csrf.rs:56-85` — `/csrf/v1/generate` is CSRF-exempt, so minting there would put the mint behind an unguarded path (B1-F5).
**Fix.** M1/M6/M7: mint only inside `create_bound_session`'s callers (log_in, login-totp, passkey login, OAuth login/link). No mint endpoint. Test: zero `device_records`/`device_account_links` rows after `POST /csrf/v1/generate` and `GET /user/v1/get`; a source guard that the two call sites carry no device header.

### F5 — Revoking the token on ban is an evasion gift, and the 1-year re-mint as specified orphans the ban; pin the record and rotate in place

**Severity: High. NEW.**
**Evidence.** `src/modules/device_v1/controller.rs:84` (`delete_for_user` — the row-deleting shape a ban handler would copy) and `m000011:11-19` (deleting rows destroys ownership history). A 1-year re-mint that inserts a **new record (new ULID)** would orphan every ban keyed on the old record id; B8 §1.1/§2.3 key bans on `device_record_id` and rotate `token_hash` in place.
**Fix.** R4/V6/D3/D6: never revoke on ban; `device_bans.device_record_id` is the key; a live ban **pins** the record (`expires_at = ban expiry + 30d`, excluded from the sweep and from the re-mint); the 1-year re-mint rotates `token_hash` **in place** (same `id`, same `first_seen_at`). Tests: `ban_pins_record_and_sweeper_skips_it`, `remint_keeps_record_id_and_ban_match`, `ban_does_not_revoke_token`.

### F6 — Three clocks (30d sliding record / 12mo ban / 1-year re-mint) hold together only when a live ban pins the record

**Severity: High. NEW.**
**Evidence.** `B8-retention-exec.md` §2.1 (`device_records` = `last_seen + 30d`; `device_bans` = 12mo from revocation), §2.3 (re-mint at 365d), §1.3 (sweep order: sessions → records → bans); `B9-second-order.md` F14 ("the linkages die at 30d, which is exactly when a 12-month ban is investigated"); DESIGN-v1 B3 ("keyed record 30d, ban row 12mo"). B9 F14's complaint (the linkage dies at 30 d) holds whenever the record is not pinned; Option B has no digest to fall back on.
**Fix.** One rule, stated once: **the investigation window equals the ban window.** A live ban pins the record (D3) so links survive; no ban ⇒ the record and its links die at 30d of inactivity; the ban row's own 12mo retention is the retention claim; the re-mint never fires under a live ban. Add the SOP sentence so the panel and the retention schedule cite the same rule.

### F7 — A 30-day `Max-Age` that is not re-set at login drifts from the sliding record, so an active user's device identity would reset every 30 days

**Severity: Medium-High. NEW.**
**Evidence.** `B1-token-storage.md` §6.2/§7a (`Max-Age=2592000`; no per-request refresh; re-set at login). `B8-retention-exec.md` §2.3 — the record slides (`expires_at = last_seen + 30d` on every login/link write). The two clocks therefore diverge in the _dangerous_ direction: a user who logs in on day 20 and again on day 40 keeps a live record but lost the cookie on day 30 ⇒ the next login mints a **new** record, and the old record's links are split from the new one — precisely the linkage the feature exists to preserve.
**Fix.** R7: on every successful login/link, re-set the **same** cookie value with a fresh `Max-Age=2592000` (the response already carries `Set-Cookie` for `ruxlog.sid` via `cycle_id()`; a second header is free). This is not a rolling per-request refresh (no hot-path write) and not a rotation (value unchanged ⇒ M4's race cannot occur). Test: `login_resets_cookie_max_age_without_changing_value`.

### F8 — The revoke UI does not exist, has two different meanings, and the only shipped "device" surface offers the wrong handle (audit-row terminate) and no list

**Severity: Medium-High. NEW.**
**Evidence.** `web/src/routes/(account)/account/+page.svelte:228-274` — the Sessions section lists `user_sessions` audit rows and terminates by audit-row id; the copy says "Devices currently signed in to your account", which reads as a device list but is a session list. `web/src/routes/(account)/account/account-view.ts:57` — `sessionDeviceLabel` is the label discipline to reuse. `web/src/routes/(application)/settings/_components/PrivacySection.svelte:109-114` — notifications appear as a **read-only status label**; there is **no** FCM revoke toggle in the UI. `web/src/lib/firebase/messaging.ts` calls only `register`/`delete`; grep for `device/v1` across `web/src` finds no caller of `/device/v1/list` ⇒ **`POST /device/v1/list` is a dormant endpoint with zero web callers**. `src/modules/auth_v1/controller.rs:1041-1093` — `sessions_terminate` is scoped per audit row; using it as the device-revoke handle would terminate a session, not a device, and the reverse (using the global record id) would revoke the device for co-users.
**Fix.** §1.5's UI: a Devices section with **link-row-id** handles (V3) and a separate record-scoped verb (V4); never the global record id as a user-facing handle; no fan-out count; session + CSRF, no fresh-auth; and either wire or delete `POST /device/v1/list` (a dormant endpoint is dead code that a future reader will "fix" by calling it).

### F9 — Token theft is attribution poisoning, and a record-level `trust_state` lets the poisoning follow the victim's browser into other accounts

**Severity: High. NEW.**
**Evidence.** `A9-crypto-keys.md` §3.2 / `C1-optionAB-audit.md` §4.1 — HttpOnly prevents reads by page scripts, **not** in-place use, and not extension reads (`chrome.cookies`). DESIGN-v1 B3 — `trust_state TEXT enum` lives on `device_records`, i.e. on the browser, shared by every account that uses it. `B5-shared-devices.md` P2/P3 — device state may never ban and every device friction must be self-clearable. A2's inheritance lemma (device, network, locale are inherited by co-users) is exactly the property that makes a record-level reputation dangerous.
**Fix.** §1.8 C1/C2 + B5 P1–P6: `trust_state` may only ever produce a self-clearable L2 challenge on a write path, never a ban, never a quota, never a login prompt; the panel must show the **edge type** ("same token" vs "same account" vs "same IP") and require a second admissible corroborator for any action; the shared-device claim clears reputation without touching `user_bans`; the record is never a ban input. Machine guard: no rule module reads `trust_state` for anything but an L2 challenge.

### F10 — The only cap in the repo is evict-oldest (data loss for evidence), and the per-account mint/fan-out cap that should replace it is absent from every report

**Severity: Medium. NEW.**
**Evidence.** `src/modules/device_v1/controller.rs:17` (`MAX_DEVICES_PER_USER = 20`) and `:20-31` (`evict_beyond_cap` deletes the **oldest** tail via `prune_owned_by_id`) — correct for delivery, data loss for evidence; the eviction is even best-effort (`:52-59`). `C1-optionAB-audit.md` §4.4 — "the per-token registration cap is therefore ~no cap against a deliberate attacker"; B9 F4 — the review queue is the attacker's cheapest lever, so unbounded records = unbounded review. Privacy-mode sessions mint a new record per session by construction (empty cookie jar at start).
**Fix.** Never evict for evidence: the record dies only by expiry/ban-pin/DSAR (D1/D3/D4). Add a **per-account new-link count** (`SELECT COUNT(*) FROM device_account_links WHERE user_id = ? AND first_linked_at > ?`, indexed) as a _review trigger_ at ~10/30d — never a block and never a challenge (a privacy-mode user legitimately exceeds it). Metric: the fan-out histogram (B5 §8) plus "records minted per account per 30d".

### F11 — Nothing in the design says what a token with no session does; the tempting implementation (a per-request sighting) is a hot-path write and a purpose-boundary violation

**Severity: Medium. NEW.**
**Evidence.** DESIGN-v1:13 ("**0 DB ops on the request path**; write on login/link; read from session payload with its own TTL; 60s ticker"); B5 §2.2 (the `route_blocker_service.rs` snapshot pattern; `scheduler.rs:9` = `TICK_INTERVAL_SECS = 60`); `web/src/hooks.server.ts:346-351,427` (the reader cache predicate is a bare cookie-presence test, so a `Path=/api` cookie is invisible to it — B1 §1). The natural "update `last_seen_at` when a token is seen" middleware would write on every authenticated request **and** track logged-out browsers, both new behaviours.
**Fix.** §1.3 U10 / §1.9 S5: the token is **inert** without an authenticated session; `last_seen_at`/`expires_at` update only in the login/link write (U3); no read on the request path; state in the policy that a logged-out browser is not tracked. Guard: a source test that no middleware in `src/middlewares/**` names the device cookie or table.

### F12 — Account deletion has no FK to lean on (by design) and no self-serve path exists, so the link cleanup must be written explicitly or the CASCADE hazard inverts

**Severity: High. NEW.**
**Evidence.** `migration/src/m000001_init.rs:48-57` — `user_sessions` has `ON DELETE CASCADE` to users; `:58-73` — `user_bans` too; `m000005_device_notification_oauth.rs:21-22` — the FCM `devices` table too. C2 §6 item 7 / B8 F12 / DESIGN-v1:43 — the device evidence tables deliberately have **no FK to users** so deletion cannot destroy the ban linkage. `src/modules/user_v1/controller.rs:269-318` + `src/db/sea_models/user/actions.rs:486-497` — `admin_delete` is the **only** deletion path (no self-serve delete anywhere in `web/`); it deletes `media_usage` + the user row in one transaction and knows nothing about device tables. `m000001_init.rs:262-263` — `audit_logs.user_id` is SET NULL on delete (the receipt shape).
**Fix.** §1.6 D4: an explicit `device_link::on_user_deleted(txn, user_id)` called from `admin_delete` (and from any future DSAR path): delete the user's link rows unless a live ban or open case references the record (then null `user_id`, copy the case id, keep the row); delete a record only when it has no remaining links and no ban; write the `audit_logs` receipt with `retained[]` (basis + until), no token, no digest. Never copy the `devices` table's CASCADE. Tests: `user_delete_keeps_ban_linked_rows_and_drops_the_rest`, `user_delete_leaves_other_accounts_links_intact`, `receipt_has_no_token_or_digest`.
