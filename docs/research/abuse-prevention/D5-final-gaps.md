## 2. The incident-response gap, stated honestly

**The 3 a.m. sequence, as the repo stands:** someone posts CSAM or a credible threat in a comment (the only
live UGC surface). There is no alert. Nothing pages anyone; there is no on-call rotation, no monitoring
dashboard, no metric that fires (`C3` F3/F4: abuse counters are dead, 429s are DEBUG). The operator finds
out when a user emails the Gmail address on the contact page, or never.

Then, even awake, the operator has:

- **no ban button** — `user_bans` has zero writers and no admin route (A8 F1, C3 F7, verified again);
- **no record of the decision** — `audit_logs` zero writers (C3 F7);
- **no notice channel** — `is_transactional` is verification+password_reset only; a suppressed address
  never receives a notice (B9 Q4); no enforcement template exists;
- **no appeal** — no table, no page, no endpoint (C4 D8);
- **no evidence freeze** — no case table, and `user_sessions` raw IP/UA has no retention policy; a
  preservation letter arriving at day 60 finds nothing (A8 §7);
- **no reporting path** — NCMEC reporting is a _statute_ (18 U.S.C. §2258A), not a feature; the runbook
  that says "hash-match, remove, report, freeze, ban" exists only as R2-ban §8 prose;
- **no content-removal path for posts** — comment hide/delete exists (`post_comment_v1`), posts are
  author/admin-gated; a post takedown is a curl command with no audit trail;
- **no legal hold** — no `legal_holds` table, no disclosure log (A8 F14).

**The minimum runbook (one page, checked into `docs/`, with a drill):**

1. **Trigger + owner**: one address (`abuse@`), one operator, one phone; a documented response window
   ("best effort, same day") that is _true_ — do not promise 24/7.
2. **Intake**: keep the comment-flag queue; add a report control for posts; make the contact page state
   what to send (URL, time, description) and what will not be read.
3. **Triage table**: (a) CSAM → remove immediately, preserve (do not delete the row), hash-match if the
   industry list is available, report to NCMEC, create the case record; (b) credible threat → preserve,
   consider LE referral, emergency-disclosure rules per R2-ban §8; (c) spam/abuse → hide/delete + notice.
4. **Freeze first**: a `legal_holds` + `legal_hold_subjects` pair and a hold-aware sweeper — otherwise the
   first retention job that ships (C4 D14) starts deleting evidence on a schedule no one can stop.
5. **Ban + notice + appeal** in one action: `user_bans` write + `enforcement_notices` row + enforcement
   mail sent despite suppression + appeal token (C4 §4's template is ready to paste).
6. **Preserve for a year** on the L7 class; access-limited storage; every read logged.
7. **Drill**: once, with a synthetic case, timed. An undrilled runbook is a document, not a capability.

Everything in that list is already _specified_ across A8/R2-ban/C4. None of it is _sequenced as one
procedure with an owner and a drill_, and that is the gap.

## 3. The skeptical reviewer's objection list

1. **"This plan does not address incident response — at 3 a.m. nobody can ban, notify, preserve, or report."**
   **Real gap, the largest one.** The components exist as fragments (A8 §7, R2-ban §8, C4 §4) but there is
   no runbook, no trigger, no drill, and no owner. At the measured base rate (C3) this is the only
   irreversible exposure.

2. **"This plan does not address mail abuse: no global send cap, no enumeration-oracle fix, an unmetered
   `/mail/v1`."** **Real gap** (§1a–1c). The per-recipient caps are good; the global ceiling and the
   bounce-reputation attack are missing, and the enumeration oracle is a deliberate shipped decision
   nobody recorded in a plan.

3. **"This plan does not address billing at all beyond 'verify commercial status'."**
   **Real gap with a sharp edge**: the module's tables do not exist, and the paywall read path 500s the
   authenticated post feed today (§2a–2b). The reviewer will ask: _does the live site work for logged-in
   users?_ Nobody has answered that.

4. **"This plan does not address what happens the day billing goes live."** **Real, latent.** No
   card-testing control, no chargeback handling, no discount redemption, client-supplied redirect URLs.
   Acceptable to defer _only_ if the plan records "billing is out of scope until a named decision".

5. **"This plan does not address the seed tooling: `seed_now` has no production guard and undo deletes by
   ID range."** **Real, narrow.** The image exclusion is verified, but C3's own fix (`seed_runs`) arms a
   destructive one-keypress undo. Fix the guard and the range-delete before adding the ledger.

6. **"This plan does not address notifications."** **Mostly acceptable.** Today the fan-out is admin-only
   and `notify_user` has zero callers, so the user-reachable flood does not exist. The residual (no
   per-recipient cap, no retention) is small; C4 already covers retention.

7. **"This plan does not address search as a DoS surface."** **Acceptable omission at this size.** A
   triple-LIKE scan at 30/min on a pool of 1 is a real but low-value target; it matters only if the blog
   ever has traffic.

8. **"This plan does not address OAuth as an account-creation path."** **Half real.** The plan's
   registration admission (D19) covers the password path only; OAuth callbacks create accounts at
   60/min/IP with no Turnstile and no per-day cap. Cheap to fold in, so the omission is a drafting gap,
   not a trade-off.

9. **"This plan does not address the unmetered public endpoints."** **Real but small.** `/mail/v1`,
   `/category/v1`, `/tag/v1`, `/feed/v1` have no limiter and no global backstop; four nest layers fix it.

10. **"This plan does not address R2/offline bandwidth exposure."** **Acceptable omission — because B3
    does.** F3/F4/F5/F6/F11 measure it and prescribe the fixes; the plan must simply adopt them, and the
    reviewer should check adoption, not re-derive the problem.

11. **"This plan does not state who does the work, with what budget, and what makes the team stop."**
    **Real gap** (B10 §6.5 raised it; C5's D1 has a falsifiable condition but no owner/budget; C6 shapes
    the plan but does not fund it). A 65–105 dev-day programme with a solo operator and no kill criterion
    is the objection the whole body of work invites.

12. **"This plan does not address that nothing in it is machine-guarded any more."** **Real and already
    covered** (B7: CI gates removed in `53d3d421`; every "machine-guarded by X" claim is a human
    promise). The objection is correct; the plan must restore PR-0 first, as B6 already sequences.

## 4. The single most important thing missing

**A tested, owned incident-response capability.** Not a control, not a table — a _procedure_: one intake
address, one triage table, a preserve-first hold, a working ban+notice+appeal action, an NCMEC/LE path,
and one drill, all scoped to the UGC that is live today (comments).

The reason it outranks everything else: every other gap in this sweep is either measurable (C3's zero base
rate), recoverable (billing tables, seed tooling, mail caps), or already planned (R2/offline by B3, the
device layer by C5/D1). This one is **irreversible**: the moment illegal content or a credible threat
appears, the ability to preserve evidence, notify the subject, take the content down with a record, and
report to the authorities is the difference between a documented, lawful response and an improvised one
that destroys the evidence it needs. The plan optimises a control for a threat with no measured base rate
while the one capability whose absence cannot be undone is specified only as scattered fragments in three
reports and is not sequenced, owned, or drilled anywhere.

Runner-up: **nobody owns the shipped-debt blocking list** (C4 §7 B1–B10). C4 says "fix before any new
feature ships"; no report assigns an owner, a date, or a verification for it — which is exactly how B7's
"human promise" gates became stale in the first place.
