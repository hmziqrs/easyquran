# Authentication hardening follow-through — 2026-10-11

Implemented the remaining application repairs from the [first audit](security-audit-2026-10-11.md) and [additional audit rounds](security-audit-rounds-2026-10-11.md). Changes are committed locally on the current branch. Deployment and owner-console verification remain separate rollout work.

## Implemented protections

| Area                        | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account trust changes       | Email changes, provider linking/unlinking, MFA setup/disable and passkey enrollment/removal require complete recent authentication. Grants are five-minute, single-use, cookie-bound and bound to credential/password/factor snapshots. Password confirmation requires enrolled MFA. OAuth/passkey-only accounts can confirm through their existing sign-in method. Name/profile edits keep their existing policy.                                                    |
| Authentication races        | A completed login cannot issue fresh permission for credentials or factors changed during that login. MFA enrollment uses a separate expiring, session-bound continuation. MFA completion/disable use conditional database writes; backup codes are consumed atomically. Delayed OAuth links carry a separate single-use continuation and recheck account security state before accepting the identity.                                                               |
| OAuth link CSRF             | Google, GitHub and Discord link initiation uses authenticated CSRF-protected POST. Provider redirects are validated on the client. Existing OAuth state and session binding remain enforced.                                                                                                                                                                                                                                                                          |
| Passkeys                    | Discoverable authentication resolves the supplied credential/user handle, loads the stored public key and verifies the signed assertion against that key. Origin, user verification, user binding, challenge ownership and counters are enforced. Counter persistence is atomic; deleted credentials and replay fail. Enrolled local MFA is completed before a full session. Registration requires a resident credential and rechecks security state transactionally. |
| Password resource admission | One shared semaphore covers password verification, dummy verification, signup, password reset/change, administrative hashing and backup-code work. Default concurrency is 2. Capacity is acquired before queuing work and held inside the blocking closure, including after HTTP cancellation. Saturation returns 429; signup preserves that status.                                                                                                                  |
| Recovery during saturation  | A transient password-work 429 preserves the exact reset grant for retry, without extending its original expiry or reviving a superseded grant. Newer issuance remains authoritative even after its token is consumed. Other reset failures keep the existing single-use behavior.                                                                                                                                                                                     |
| Push privacy                | One token belongs to one account. Migration revokes historical cross-account duplicates and enforces uniqueness. Registration/deletion include an expected owner; obsolete browser work is aborted and owner/generation checked. Logout/account changes revoke subscriptions. Both server and service worker send/display generic push text; private details remain behind authenticated API access.                                                                  |
| Guard APIs                  | Removed unused requirement-builder methods that silently did nothing and a guard layer that forwarded requests without enforcement. Anonymous sessions cannot satisfy verified/unverified/role requirements simply because an explicit authenticated flag was omitted. Contradictory authenticated/anonymous requirements fail closed.                                                                                                                                |
| Production configuration    | Production rejects insecure cookies and empty trusted ingress CIDRs. Password registration fails closed with 503 when Turnstile's secret is missing; development can still run without a secret.                                                                                                                                                                                                                                                                      |
| Dependencies                | Upgraded AWS S3 dependencies and Ratatui to maintained versions resolving the LRU advisories. Replaced unused terminal bridge dependency, moved migration entrypoint to Tokio, removed async-std/paste paths and upgraded the dependency parent that retained vulnerable rkyv. Terminal dependencies are optional under seed-system.                                                                                                                                  |
| Publication                 | Existing image workflow now requires complete web/Rust checks and dependency policy checks before publication. Actions use verified commit pins; checkout does not persist credentials. Registry writes additionally require a raw non-PR event check. Existing master publication still triggers Dokploy deployment.                                                                                                                                                 |

Three implementation agents covered account trust, passkeys and push ownership. Independent cross-review then examined fresh-auth races, password admission, recovery retry, CI policy and account-switch privacy. Findings from cross-review were repaired before final validation. Tests use isolated application databases and local mocks; no production pushes, account mutation or load tests were performed. Quran databases were not modified, provisioned, committed or hashed.

## Evidence and limits

Validation results are recorded after final gates below. Regression cases include real signed ES256 assertions, invalid key/origin/user handle/user-verification/counters, deleted credentials, challenge reuse, cookie/factor changes, competing backup-code consumption, account-switch transport races, cancelled password work and dependency activation.

The full Cargo lockfile audit still reports **rsa 0.9.10 / RUSTSEC-2023-0071**. Upstream has no patched version in the checked release line. It is absent from the compiled Linux workspace graph for the deployed arm64 target with vendored OpenSSL. The publication policy displays this finding and fails if that exact package/version becomes reachable. It also rejects new advisories, unsound/unmaintained/yanked findings and operational/parser errors. This is a narrowly checked exception, not a clean whole-lockfile audit. [RustSec RSA advisory](https://rustsec.org/advisories/RUSTSEC-2023-0071.html).

LRU remediation follows the [RustSec panic-safety advisory](https://rustsec.org/advisories/RUSTSEC-2026-0253.html). rkyv removal follows the [archive validation advisory](https://rustsec.org/advisories/RUSTSEC-2026-0235.html). Fresh-auth/factor controls follow [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#reauthentication-after-risk-events) and [MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html). Admission budgeting follows OWASP's [password hashing cost and denial-of-service guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#using-work-factors). Stored-key discovery follows the installed [WebAuthn-rs API](https://docs.rs/webauthn-rs/latest/webauthn_rs/struct.Webauthn.html).

## Rollout

Follow [deployment instructions](../deploy/README.md#4-first-deploy--verify): configure both Turnstile keys, actual trusted proxy CIDRs and secure cookies; deploy web/API together; apply application migration m000011; re-enable revoked browser subscriptions. Existing non-resident passkeys may need enrollment again for discoverable login. Fresh-auth proofs are intentionally process-local and disappear safely on restart.

Verify Cloudflare/Traefik origin restrictions, edge quotas, Turnstile allowed hostnames, effective cookies/CSP/private caching, Firebase rules/API restrictions, repository secret/dependency alerts and production protection using the owner's consoles and an owned test account. The published site returned Cloudflare 403 during read-only audit requests; those controls remain unverified. Previously identified historical invalid media references still need a read-only operational review rather than an automatic rewrite.

These repairs cover confirmed findings and the reviewed paths. They do not certify every legacy feature or cloud configuration as secure.
