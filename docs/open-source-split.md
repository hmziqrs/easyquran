# Open-sourcing EasyQuran: public app repo + private layer

Status: design document. Nothing here is implemented yet.

## 1. Goal

Publish EasyQuran as a real open-source application, holding back a thin proprietary layer,
and move release builds off the dev laptop into GitHub Actions.

The concrete payoff is CI cost. Standard GitHub-hosted runners are unlimited and free on
**public** repositories and billed on private ones, and that includes `ubuntu-24.04-arm` —
which matches the arm64 Ubuntu deploy target exactly, so the Rust binary compiles natively
instead of being cross-compiled. Today `just images` / `just push` build on an Apple Silicon
Mac via `cargo-zigbuild`; that costs nothing but pins every release to one machine.

Non-goals:

- No rewrite or re-architecture of the Quran modules. The backend is a port of an
  already-open-source boilerplate (billing, analytics, admin TUI, seeding, auth, bans,
  the `rux-*` crates), so nearly all of the server side can be published as-is.
- No change to how translations reach the VPS. The compose bind mount
  `./db/quran/tanzil:/app/quran:ro` stays exactly as it is.

## 2. Topology

```text
PRIVATE  hmziqrs/easyquran        source of truth. Everything lives here, unchanged.
                                  Dokploy keeps cloning this (it needs db/ for the bind mount).
PUBLIC   <org>/easyquran          GENERATED by `just publish-public`.
                                  The app + fallbacks + Dockerfiles + workflows.
                                  Builds standalone. Runs the free arm64 CI.
```

Day-to-day work does not change: one working tree, the private monorepo. The public repo is
an **export**, never hand-edited. During a release, CI checks out the public repo and pulls
the private layer back out of the monorepo at a **pinned commit SHA**, so the two halves
cannot drift.

Which org: `oxlabs-dev` and `freeoxide` already exist; a dedicated org for the project is
cleaner and is the recommendation. Open decision.

Inverting this later — making the public repo primary and keeping a small private repo for
the layer plus data — is attractive but deferred. Dokploy's clone must contain `db/`, so
the inversion also requires deciding how 356 MB of translations reach the host.

## 3. What stays private

| Path | Why |
| --- | --- |
| `rust/backend/api/src/quran/store.rs`, `translation_pool.rs` | Quran DB pooling and cache |
| `rust/backend/api/src/modules/quran_v1/cache.rs` | response cache |
| `web/src/lib/offline/**` | OPFS pack/eviction engine |
| `web/src/lib/boot/offline-engine.ts`, `lib/workers/quran.worker.ts`, `src/service-worker.ts` | worker + SW side of the same engine |
| `web/src/lib/quran/{offline.ts,wasm-query-runner.ts,worker-client.ts,range-fetch.ts}` | client-side sqlite query path |
| `web/src/lib/stores/{verse-cache.svelte.ts,stacked-translations.svelte.ts}` | in-memory cache policy |
| `web/src/lib/server/quran-disk-cache.ts` | SSR 7-day disk cache |
| `web/src/lib/quran/search/**`, `lib/quran/search.ts` | search |
| `web/src/lib/search/palette/sources/quran-*.ts` | 4 of the 6 palette sources |
| `rust/backend/api/src/quran/{search.rs,normalize.rs}` | search + Arabic normalization |
| `web/src/routes/(application)/app/_reader/**` (5,436 LOC) | reader layout engine |
| `web/src/lib/reader/**`, `lib/quran/view/**` (except `source-profiles.ts`) | reader coordinate/presentation model |
| `web/src/lib/stores/reader*.svelte.ts` | reader state machine |
| `db/quran/tanzil/translations/{sqlite,sql,scripts,index.json,index.min.json}` | 356 MB — held back for size, not secrecy |
| `docs/**`, `bench/**`, `ROADMAP.md`, `AGENTS.MD`, `CLAUDE.md`, `.claude/**` | internal; zero build impact |

Everything else is published, including the entire backend boilerplate.

### Three things that must be public even though they look private

1. `db/quran/tanzil/arabic/quran-uthmani.sqlite` (1.6 MB) and `quran-simple-clean.sqlite`
   (930 KB), plus `quran-data.xml`. Prerender opens the Uthmani DB directly through
   `node:sqlite` — see `web/src/lib/server/quran-sqlite.ts:27-53`, which throws
   `[quran-sqlite] missing <id> DB at <path>` if it is absent. Without these two files the
   public repo cannot build at all. They are Tanzil data, not proprietary.
2. `web/src/lib/data/translations.json` and `web/src/lib/quran/view/source-profiles.ts` —
   the **baked id maps**. Per `docs/quran-system.md` these are the security boundary for
   artifact downloads: production Quran bytes, size and path come from these maps and never
   from remote metadata. They are also read by `web/vite-plugin-quran.ts` at Vite config
   time. Hence the carve-out: `lib/quran/view/**` is private, `view/source-profiles.ts` is
   not. The manifest must spell that exception out.
3. `web/static/quran-meta/quran-data.json` (16 KB) — `web/src/lib/server/quran-data.ts`
   throws at module init if it is missing.

## 4. Public fallbacks, not stubs

Holding back the reader, search and the offline engine means the public repo is not a
drop-in copy of the deployed app. To keep it a genuine project rather than a husk, every
private module leaves behind a **working but naive** implementation:

| Private module | Public fallback |
| --- | --- |
| reader layout engine | plain vertical ayah list; no mushaf pagination, no line layout |
| search | naive substring match over normalized text |
| offline engine | direct network fetch; no OPFS, no worker, no service worker precache |
| backend pool + cache | open the sqlite per request; no pool, no response cache |

With those in place the public app installs, builds and reads the Qur'an end to end. The
private layer is a performance-and-polish overlay on top of it, which is an honest
description of what it actually is.

Cost to state plainly: **the fallbacks are hand-maintained.** Change an exported signature in
the private layer and the public repo's build job goes red until the fallback is updated.
That is the recurring tax of this design, accepted deliberately in exchange for not
refactoring `AppState`, `docs.rs` and the abuse subsystem to make the seam disappear.

## 5. Mechanism

### 5.1 One boundary definition

`deploy/public-manifest.txt` — rsync filter rules listing the private paths from §3,
including the `source-profiles.ts` exception. Both the export script and the CI injection
step read this same file, so they cannot disagree about where the line is.

### 5.2 Export: `just publish-public`

`scripts/publish-public.ts`, run on the dev machine:

1. Refuse to run if the monorepo working tree is dirty. Record `git rev-parse HEAD` as `SHA`.
2. Clone or fetch the public repo into a scratch directory.
3. `rsync -a --delete --filter="merge deploy/public-manifest.txt"` monorepo → clone.
4. Overlay `deploy/public-fallbacks/` (the §4 implementations, kept in the monorepo) on top.
5. Write `.private-layer-sha` containing `SHA`. This is what pins the injection.
6. Commit `chore: sync from private @ <short-sha>` and push.

The public repo starts empty, so the monorepo's 107 MiB pack (234 tracked sqlite/sql blobs,
no LFS) never migrates and no `git filter-repo` run is needed. Public history is one commit
per sync.

### 5.3 CI: two workflows in the public repo

**`base-build.yml`** — on every push and PR. Builds web and api with the fallbacks only, no
private access. This job is what proves the public repo is a real project; if it ever needs
a private file, the split is fake and the job says so.

**`release.yml`** — `workflow_dispatch` (input: version) and `v*` tags only. Never
`pull_request`: fork PRs must not see the deploy key. The job runs inside a GitHub
Environment with required reviewers, so a collaborator cannot exfiltrate the secret by
pushing a workflow.

```text
runs-on: ubuntu-24.04-arm          # free, and native arm64
  checkout public
  ssh-agent <- secrets.PRIVATE_LAYER_KEY     # read-only deploy key on hmziqrs/easyquran
  git clone --filter=blob:none --no-checkout private
    sparse-checkout = private paths from deploy/public-manifest.txt
    git checkout $(cat .private-layer-sha)
  rsync private paths over the fallbacks
  rm -rf the private clone's .git            # never let it into a docker context
  pnpm install --frozen-lockfile
  PUBLIC_ENV=prod pnpm --filter web build
  cargo build --release -p ruxlog            # native: no cargo-zigbuild, no vendored-openssl
  docker build -f deploy/Dockerfile.web ... && docker push
  docker build -f deploy/Dockerfile.api ... && docker push
```

Notes:

- `deploy/Dockerfile.api` currently hardcodes
  `rust/target/aarch64-unknown-linux-gnu/release/ruxlog`, the zigbuild output. Native CI
  produces `rust/target/release/ruxlog`. Parameterise it with `ARG BIN_PATH` so the laptop
  and CI paths share one Dockerfile. The `vendored-openssl` feature and `cargo-zigbuild`
  stay for local builds; CI needs neither.
- **No build-time secrets exist.** Web has exactly one build-time variable, `PUBLIC_ENV`
  (must be `local` or `prod`, defaults to `prod` on `vite build`); the api has none — no
  `build.rs`, no sqlx offline, no `include_bytes!`. Everything else is `$env/dynamic/*` read
  at runtime.
- Leak discipline: no `set -x`, no `upload-artifact` carrying source, and
  `persist-credentials: false` on the private clone step.

### 5.4 Release path

`just release v1.0.0` → `publish-public` → `gh workflow run release.yml -R <org>/easyquran
-f version=v1.0.0` → Dokploy redeploy.

## 6. Where the images go

Registry stays GHCR, but the namespace follows the **public** repo's owner. If the public
repo lands in an org, coordinates become `ghcr.io/<org>/easyquran-{web,api}` and `REGISTRY`
must be updated in `.env` / `deploy/.env.example`, `docker-compose.yml`'s
`${REGISTRY:-ghcr.io/hmziqrs}` defaults, the `justfile` header, and the Dokploy registry
entry. Keeping the public repo under the personal account leaves `ghcr.io/hmziqrs` as-is.

### 6.1 Pushing from CI

No PAT and no registry secret. `GITHUB_TOKEN` is sufficient:

```yaml
permissions:
  contents: read
  packages: write
steps:
  - uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}
```

Then push `ghcr.io/<owner>/easyquran-web:<version>` and `:latest`, same for the api. The
package auto-links to the repo it was pushed from. So the public repo needs exactly **one**
secret in total: `PRIVATE_LAYER_KEY`, the read-only deploy key for the injection step.

### 6.2 Visibility

The published images contain the compiled private layer — SvelteKit output is readable
JavaScript — so the **packages must stay private** even though the source repo is public.
Publishing them publicly would defeat the split entirely.

This is the default and requires no action: a package's first publish is private, and a
package linked to a repository inherits that repository's *access permissions* but **not**
its *visibility*. A public source repo therefore does not make the image public. The rule is
simply: never flip it.

Consequence: anonymous `docker pull` of the release images returns `denied`. Only accounts
granted read access — and the PAT Dokploy uses — can fetch them. Note that this protects
only the private layer; everything in the public repo is readable source by definition, and
anyone can build a working app from it using the §4 fallbacks.

Optional, if a publicly pullable demo is ever wanted: have `base-build.yml` push a
fallback-only image under a separate name (`easyquran-web-oss`) and set *that* package
public. The release images stay private.

### 6.3 Pulling on the VPS

Unchanged from today: the private package needs a registry credential in Dokploy, a PAT
scoped `read:packages`. The only thing that changes is the username/namespace if the repo
moves to an org.

### 6.4 Cost

Private container storage and bandwidth on GHCR are currently free. Nothing about the cost
picture changes: builds move from the Mac to free public runners, images stay private and
free, the VPS bill is unchanged.

## 7. Pre-work before the first export

- `rust/backend/api/src/utils/cors.rs` — production boot currently asserts that
  `ALLOWED_ORIGINS` contains `https://easyquran.fyi` (the `EASYQURAN_ORIGIN` constant).
  Nobody else can run the public repo in production until that is config-driven.
- `rust/backend/api/src/quran/normalize.rs:128` `include_str!`s
  `web/src/lib/quran/__fixtures__/parity.json`. Both are private, so they stay on the same
  side of the line — but the CI injection must fetch the fixture too or `cargo test` breaks.
- Other hardcoded product identity worth neutralising while there: the
  `x-easyquran-internal-token` header name in `utils/client_ip.rs`, and the domain literals
  in `utils/webauthn.rs`.
- Add a LICENSE. Tanzil is already credited on the About page (commit `75a9cc5`).
- Decide the org and create the repo.

## 8. Verification

1. **Public repo is genuine.** In a clean clone with no private access:
   `pnpm install && PUBLIC_ENV=prod pnpm --filter web build` and
   `cargo build --release -p ruxlog` both succeed, and the running app serves a readable
   surah. This is `base-build.yml`.
2. **Boundary holds.** `git grep` the public clone for `translations/sqlite`, `_reader`, and
   the other private manifest strings → zero hits. `git count-objects -vH` on the public repo
   stays under ~10 MB.
3. **Injected build matches the laptop build.** Run `release.yml` at a tag, then locally
   `just images <tag>`; compare `docker image inspect` digests for the api binary layer and
   the web `build/` layer.
4. **Runtime smoke on the VPS**, the same checks used for commit `f4c3832`: `/` 200,
   `/app/al-fatihah` 200, `/health/quran` 200, api `/healthz` and `/quran/health/ready` 200,
   and `/app/al-fatihah/t/en/arberry` 307 → 200 (proves the web→api internal SSR path and
   that all 115 translations resolved through the bind mount).
5. **Monorepo gates green** after the `cors.rs` change and the manifest work: `pnpm check`,
   `pnpm lint`, `pnpm test`, plus `cd rust && cargo test --workspace`.

## 9. Phasing

1. Manifest + fallbacks. This is the bulk of the work, iterated against a red build.
2. Export script and the first public push.
3. `base-build.yml`, then `release.yml` and the `ARG BIN_PATH` change.
4. Fold the Dokploy redeploy into `just release`.

The laptop build path (`just images` / `just push`) stays intact throughout, so releases are
never blocked while this lands.
