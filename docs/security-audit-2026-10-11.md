# Authentication security audit — 2026-10-11

Confirmed authentication weaknesses were reproduced locally and patched. These changes need a new API deployment before they protect the published application. Infrastructure and cloud account settings remain unverified.

## Scope and limits

Reviewed password login, recovery, verification, OAuth identity linking, session revocation, account changes, authenticated data ownership, browser authentication handling, deployment ingress, dependency advisories, and tracked Git history. Audit started at `c0602d53`; concurrent documentation and popup changes were preserved.

Tests use isolated application SQLite databases. Quran databases were not modified, versioned, provisioned, or hashed. No production accounts, emails, or data were changed. Read-only requests to `https://easyquran.fyi/`, `/login`, `/api/quran/health/ready`, and `/api/user/v1/get` all received Cloudflare HTTP 403. That prevents conclusions about deployed cookies, headers, origin access, or login behavior.

Severity describes the pre-patch code and its prerequisites, not evidence of a real-world compromise.

## Confirmed findings and fixes

| Finding                                                                         | Severity | Previous behavior and impact                                                                                                                                                                                                                                | Implemented solution                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OAuth accounts merged by matching email                                         | High     | A previously unlinked provider identity could inherit an existing local account solely through a matching verified provider email. Local ownership and provider ownership were conflated, including unverified local accounts and recycled email addresses. | Existing accounts require authenticated explicit linking. Login uses the already-linked provider subject. Legacy Google subject bindings migrate without email matching; conflicting ownership is rejected. New account and identity creation commit together.                        |
| Recovery codes survived account changes and lacked account-wide guessing limits | High     | Changing IPs bypassed the recovery verification budget. A code issued to an old address could remain associated with the account after its email changed. Separate lookup and deletion also allowed competing requests to observe the same valid code.      | Add normalized-email request and verification budgets alongside IP limits. Verify and consume the exact unexpired code in one transaction. Email changes delete recovery and verification codes atomically. Issuance checks the current address inside its transaction.               |
| Reset grants survived credential rotation                                       | High     | A previously issued reset token remained usable after the owner changed credentials.                                                                                                                                                                        | Bind each grant to the account's current session authentication secret and check it inside the password-update transaction. Rotate that secret on password changes; supersede previous grants for the same account. Grants remain single-use with a ten-minute TTL and a bounded map. |
| Email verification used stale state                                             | High     | A code sent to a previous address could verify a changed address, and verification used separate database operations with best-effort consumption.                                                                                                          | Consume the unexpired code and verify the exact current account email atomically. Reject stale resend requests; delete outstanding codes on email changes.                                                                                                                            |
| Administrative credential changes preserved old sessions                        | High     | Admin password replacement did not rotate the session authentication secret, so existing sessions remained authenticated.                                                                                                                                   | Rotate the secret on admin changes to password, email, role, or verification trust. Admin email changes also invalidate pending codes.                                                                                                                                                |
| Session revocation errors granted access                                        | Medium   | A revocation backend error was treated as “not revoked”; poisoned revocation state also returned a successful negative result.                                                                                                                              | Reject authentication when the revocation check fails. Backend errors propagate, and warning logs omit session identifiers.                                                                                                                                                           |
| Google unlink retained a legacy sign-in path                                    | Medium   | Removing the modern identity row left `users.google_id`, allowing the old Google identity to sign in again.                                                                                                                                                 | Clear the legacy binding when the Google identity is removed, within the existing unlink transaction.                                                                                                                                                                                 |

Explicit federated linking follows [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#secure-federated-account-linking). Recovery changes follow [OWASP password recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), particularly single-use, expiry, and guessing limits.

## Secret-history review

Gitleaks scanned 768 commits and reported five matches. Four are test fixtures: a deliberately incorrect proxy token, an offline JWT signing key, sample object-storage credentials, and a webhook test secret. The fifth is Firebase's public browser configuration key. No production credential leak was confirmed by these matches; this does not certify every past or external secret.

The Firebase browser key identifies the project and is public by design. Authorization depends on Firebase Security Rules and related controls. Verify its API allowlist and quotas in the cloud console; do not allow unrelated billable APIs. These settings could not be inspected locally. See [Firebase API-key guidance](https://firebase.google.com/docs/projects/api-keys). Secret values are deliberately omitted from this report.

## Remaining work, in priority order

1. **Deploy the tested changes and validate ingress.** Ensure the origin accepts external traffic only from Cloudflare, using a tunnel, authenticated origin access, or a firewall allowlist. The API trusts `CF-Connecting-IP` for external identity; a reachable origin that accepts forged headers defeats IP budgets. Follow `deploy/README.md`'s ingress verification procedure. Confirm deployed Secure/HttpOnly/SameSite cookies, CSRF rejection, CSP, and authenticated cache isolation using an owned test account.
2. **Require recent authentication for account trust changes.** Current session authentication permits profile email changes, provider linking/unlinking, and passkey enrollment without a separate recent-authentication requirement. Add a session-bound `reauthenticated_at` grant, valid for roughly five minutes, obtained through password, passkey, or provider reauthentication and the configured second factor. Check it server-side before changing email or sign-in methods. A stolen live session otherwise has a route to persistent control. This requires coordinated API and account UI work.
3. **Make security checks deployment gates.** The image workflow builds and publishes but does not run the full check/lint/test suites or dependency audits. Add required read-only CI jobs, gate image publication on them, enable secret scanning and dependency alerts, and use reviewed narrow exceptions only for demonstrated unreachable advisory paths. Keep production tokens out of fork workflows.
4. **Bound password-work concurrency.** Password verification and dummy verification use `spawn_blocking` without a shared admission limit. Add a bounded semaphore with short acquisition timeout before Argon2 hashing/verification, including signup and recovery paths. Configure edge limits and registration Turnstile in production. Load-test against a disposable environment to size the budget; no production load test was performed.
5. **Resolve remaining dependency advisories and verify Firebase settings.** Use the dependency table above; retain audit failures as visible maintenance work. Confirm Firebase API restrictions, permitted authentication domains, unused-service access rules, and quotas in the owner console.
6. **Choose the recovery privacy policy explicitly.** The recovery endpoint intentionally returns “No account exists for that email” for unknown addresses. Rate limits reduce harvesting but do not eliminate the account-existence oracle. If account membership should be private, return the same status/body for existing and unknown addresses and avoid distinguishable synchronous delivery timing. This audit preserved the documented product decision.

## Release behavior

No schema migration is required. A provider with an email matching an existing account must now be linked from the signed-in Account screen. Already-linked identities resolve by stable provider subject, allowing provider email changes when provider-specific validation passes. Legacy Google bindings migrate on successful subject-based login. Old recovery/verification codes are invalidated when the account email changes; old reset grants fail after credential rotation. Revocation backend failures now deny authentication until the backend recovers.
