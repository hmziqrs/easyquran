# Additional security audit rounds — 2026-10-11

This continues [the first audit](security-audit-2026-10-11.md). Internet research and independent reviews found nine additional security weaknesses, plus a passkey availability defect and a conditional notification privacy concern. The fixes below are local changes until the API and web application are redeployed.

## Research priorities

The current published baselines are [OWASP Web Top 10: 2025](https://top10.owasp.org/2025/), [API Top 10: 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/), and [ASVS 5.0.0](https://owasp.org/projects/asvs). These guide coverage; this work is not an ASVS certification. The following priorities reflect this application's cookie sessions, provider logins, account settings, durable offline data, and mounted legacy API modules.

## Rounds and evidence

The first audit covered identity linking, recovery, verification, revocation, dependencies and tracked secrets. This additional discovery round used separate authentication-state, API-authorization and browser-boundary reviewers, each tracing reachable routes through middleware, handlers and storage. A separate web implementation worker handled account isolation. Local regressions use isolated application databases and fake transports; no production accounts or notifications were used.

The follow-up round examines alternate ID paths, races and the fixes from another perspective. Findings are reported as code weaknesses with prerequisites, not evidence of an observed compromise. No Quran database was modified, provisioned, versioned or hashed. Concurrent work in another chat is excluded from this security commit.

## Additional findings and solutions

| ID    | Severity          | Confirmed previous behavior                                                                                                                                                                                                                                                                          | Solution                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R2-01 | High              | Shared `finish_oauth_login` issued a full session for an account with local TOTP enabled. All five provider login implementations reached it. A compromised linked provider session therefore bypassed the local factor.                                                                             | Shared login creates a pending proof instead. Browser callbacks use `/auth/{provider}/totp`; native/exchange responses return a factor-required envelope. Existing factor completion is the only path to a full session. Linking from an already authenticated account remains separate.                                                                                                                  |
| R2-02 | Medium            | TOTP setup immediately replaced an enrolled factor and set `two_fa_enabled=false`, before replacement verification. Abandoning setup left a password-only account indefinitely.                                                                                                                      | Reject setup while enrolled, preserving the current factor. Users must deliberately disable it through the existing factor-authorized flow before enrolling a replacement. This makes removal explicit; an atomic pending-factor replacement would be a future UX improvement.                                                                                                                            |
| R2-03 | Medium            | Password-to-TOTP grants contained only user ID and issuance time. Credential rotation did not invalidate earlier first-factor proof. Completion still required a valid second factor.                                                                                                                | Shared single-use five-minute grants bind the originating cookie session, account authentication secret and enrolled factor. Bound the store and supersede prior proof from that session. Reject stale or disabled factors before issuing a session.                                                                                                                                                      |
| R2-04 | Medium            | A 14-day inactivity timeout had no absolute age check, despite storing `authenticated_at`. A regularly used stolen session could continue indefinitely.                                                                                                                                              | Enforce 14-day absolute authenticated age in both session acceptance paths, independently of inactivity expiry.                                                                                                                                                                                                                                                                                           |
| R2-05 | Medium            | Public comment listing ignored parent publication status; verified users could create or flag comments on hidden parents by ID. Unpublishing a post did not hide its comments.                                                                                                                       | Check the parent on list/create/flag. Published posts retain public access; hidden parents require their author or moderator. Check and mutation share a transaction. Existing moderation and comment-owner restrictions remain.                                                                                                                                                                          |
| R2-06 | Medium            | An author could assign someone else's numeric media ID as their post's featured image. Post responses exposed media otherwise restricted by its direct API.                                                                                                                                          | Validate attachment ownership inside post create/update transactions. Existing invalid references need a read-only operational audit; this patch does not silently rewrite historical data.                                                                                                                                                  |
| R2-07 | Medium            | `/en//attacker.example`, `/app//attacker.example` and composed variants emitted an off-origin protocol-relative redirect. Raw backslashes could canonicalize to the same case.                                                                                                                       | Validate the final parsed redirect origin and reject malformed paths with an uncached 400. Preserve normal legacy mappings and same-origin encoded separators.                                                                                                                                                                                                                                            |
| R2-08 | Medium            | A single ownerless bookmark queue could upload A's private folder edits through B's cookie. A delayed A response also repopulated B's view after logout. The cleanup lived in a layout absent from account routes.                                                                                   | Partition the durable outbox by account, discard legacy unowned entries, handle account changes globally, and guard transport, response and optimistic work by generation/owner. | R2-09 | High, conditional | Mercado Pago HMAC covered query resource ID, request ID and timestamp, while normalization trusted unsigned body IDs, user, amount and status. A captured fresh delivery signature could accompany substituted billing metadata. Pending/rejected payments were also treated as checkout completion. | Match body ID to signed ID, validate identifiers, fetch the resource from the authenticated fixed provider API, and derive all fields/status from that response. Unknown topics cannot become arbitrary canonical billing events. Pending payments leave the checkout intent available for later approval. Exploitability depends on this provider being configured and obtaining valid delivery headers. |

Redirect validation follows [OWASP redirect guidance](https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html). ## Remaining findings and deployment work

1. **Recent authentication for account trust changes remains necessary.** Implement a short, session-bound fresh-authentication grant before email changes, provider linking/unlinking and passkey enrollment. Validate password/passkey/provider proof and configured MFA. The unused `totp_verified`, `totp_if_enabled` and `reauth_within` requirement-builder methods are currently no-ops; do not use them as security enforcement. The mounted application uses separate functioning guards.
2. **Password-work admission remains unbounded.** Introduce one shared semaphore covering Argon2 verification, dummy verification, signup, password reset/change and backup-code hashing. Hold its permit inside the blocking closure so cancelling HTTP work cannot release capacity while CPU work continues. Fail promptly under saturation; size the budget against container CPU/memory in a disposable environment. Enable edge budgets and production registration Turnstile.
3. **Passkey login has a verified availability defect.** WebAuthn authentication starts with an empty credential list and finishes before loading the saved public key. The installed library rejects the assertion, so this is not a successful signature bypass. Use properly verified discoverable authentication, resolve the credential and user handle, load the stored key, require user verification and atomically update counters. Alternatively use username-first authentication with the actual credential list. Test a valid signed assertion, wrong key/user handle, replay and credential deletion. Do not weaken verification to make the current empty-list flow succeed.
4. **Push notification account ownership needs coordinated repair if FCM is enabled.** Backend devices can map the same token to different users; account-specific notification titles/body/data are sent to registered devices. The web persists tokens across logout and skips registration when a token is unchanged. Its raw device POST also lacks the required CSRF header, so successful current web registration was not demonstrated. Repair transport through AuthClient, bind one active account to a browser subscription, unregister/delete it on account changes, reject obsolete refresh work, and use generic push content for privacy while private details stay behind authenticated API access. Test logout, offline failure and account switch before enabling this path. No production pushes were sent.
5. **Restrict production ingress and verify deployed controls.** Follow `deploy/README.md`. The first audit's read-only requests received Cloudflare 403, so origin exposure, effective cookies/CSP/cache rules and edge quotas remain unverified. Validate with an owned test account after deployment.
6. **Make tests and dependency checks publication gates.** The current image workflow builds/publishes without the complete checks. Keep the first audit's unresolved Cargo advisories visible, review actual deployed feature reachability, and avoid blanket ignores. Enable dependency/secret alerts and protect production keys. Firebase project restrictions and rules still require owner-console verification.

The initial audit's dependency table, secret-history triage and deliberate recovery account-existence response remain applicable. These changes do not establish that every mounted legacy feature or cloud setting is secure.
